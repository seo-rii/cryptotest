# 8. 블록암호 - 변형 AES 7라운드

## 문제

`plaintext.bin`과 `ciphertext.bin`에는 동일한 master key로 암호화한 50,000개 평문/암문 쌍이 들어 있다. 암호는 변형된 7라운드 AES다.

라운드 구조:

```text
X^0 = P
for i = 0..6:
    Y^i = SB(X^i)
    Z^i = SR(Y^i)
    W^i = MC(Z^i)
    X^{i+1} = W^i xor k_i
C = X^7
```

표준 AES와 달리 초기 AddRoundKey가 없고, 마지막 라운드에도 MixColumns가 있다. 라운드키는 master key byte의 permutation과 일부 `MC` 적용으로 만들어진다.

`leaked.txt`에는 배열의 0-based index `28178`, 즉 자연어로 28,179번째
평문의 일부 중간 state bit가 기록되어 있다. 목표는 16바이트 master key를
복원하는 것이다.

## 배경지식

### AES state layout

AES는 16바이트 state를 4x4 matrix로 보며, 표준 구현에서는 column-major layout을 사용한다.

```text
state index = row + 4*column
```

SubBytes는 byte별 S-box, ShiftRows는 row별 rotate, MixColumns는 column별 GF(2^8) 선형 변환이다.

### 문제 힌트와 실제 공격의 관계

Demirci--Selcuk 공격은 5라운드 distinguisher를 바탕으로 AES-192의 7라운드와
AES-256의 8라운드를 공격하는 reduced-round AES 기법이다. 이 문제의
solver는 그 distinguisher를 구현하지 않는다. 문제에서 훨씬 강한 중간
state leak와 특수한 round-key permutation을 주므로, 여기서는 여러 leak
completion을 미리 계산하고 같은 master-key byte를 공유하는 조건으로
후보를 결합하는 관점만 사용한다. 따라서 이 풀이의 정확한 명칭은
**leak-assisted bidirectional key-byte constraint join**이다.

이 문제에서는 다음 정보가 공격에 쓰인다.

- 많은 known plaintext/ciphertext pair
- 특정 pair의 여러 라운드 중간 state bit leak
- 라운드키가 master key의 단순 permutation/MC로 만들어지는 구조

## 풀이

### 1. leak index 검증

문제의 leak index `28178`은 0-based다. 파일에서 해당 pair를 읽으면 다음과
같다.

```text
P[28178] = b3a6db3c870c3e99245e0d1c06b747de
C[28178] = 0b764cbfd5a347a13b41b4fdd5b11e00
```

이는 `leaked.txt`의 `X^0`과 `X^7` 전체 byte와 일치한다.

### 2. 직접 복원되는 key byte

표준 AES column-major layout을 가정하면 첫 라운드에서

```text
X^1 = MC(SR(SB(X^0))) xor k0
```

이다. `leaked.txt`에는 `X^1[0] = 0x20`이 완전히 주어져 있다. 따라서

```text
k0[0] = MC(SR(SB(X^0)))[0] xor X^1[0]
```

계산 결과:

```text
K[0] = 0x29
```

문제의 key schedule 정의상 `k0`는 master key `K` 자체이므로 master key 첫 byte도 `0x29`다.

마지막 라운드 쪽에서도 직접 복원되는 byte가 있다. 문제의 key schedule에서

```text
k6 = MC(K[1], K[5], K[7], K[14], K[15], K[8], K[0], K[4], ...)
```

이고 `X^7 = MC(SR(SB(X^6))) xor k6`이다. ciphertext column에 `InvMC`를 적용하면 key schedule의 `MC`가 선형성으로 풀린다.

```text
InvMC(C column 0) xor [K1, K5, K7, K14] = SR(SB(X^6)) column 0
InvMC(C column 2) xor [K9, K13, K3, K6] = SR(SB(X^6)) column 2
```

`X^6[0]`, `X^6[2]`가 완전히 leaked 되었으므로 다음이 나온다.

```text
K[1] = 0x23
K[3] = 0x84
```

### 3. 후보 집합 축소

`X^3 -> X^4`의 대각선 leak는 네 개의 독립된 4-byte group으로 나뉜다. `k3`는 master key permutation만 적용된 round key이므로 다음 후보 집합을 얻었다.

```text
K[10] candidates (32)
K[11] candidates (16)
K[12] candidates (32)
K[13] candidates (32)
```

또한 `X^2[0..3]`는 16개의 column 후보뿐이다. `MC`의 선형성을 이용하면

```text
InvMC(X^2 column 0) = SB(X^1 diagonal) xor [K5, K8, K6, K3]
```

이고, 이미 구한 `K[3]=0x84` 및 `K[10]` 후보와 결합해 다음 compact relation으로 줄어든다.

```text
combined X^2/K[3]/K[10] relation candidates = 512
unique K[5] candidates  = 16
unique K[8] candidates  = 16
unique K[15] candidates = 16
unique K[6] candidates  = 192
```

이 후보들은 다시 `X^3 = F(X^2) xor k2`를 거꾸로 풀 때 쓰인다. `k2` column 0은 이미 알려진 key byte만 포함하므로 `InvF(X^3 xor k2)`의 세 byte가 `K[2]`, `K[4]`, `K[14]`를 순차적으로 고정한다.

최종 복구된 master key:

```text
K = 2923be84e16cd6ae529049f1f1bbe9eb
```

### 4. Leak 기반 후보 join

최종 구현이 사용하는 leak 구조는 다음과 같다.

- `X^1[0]`: 완전 1바이트
- `X^2[0..3]`: 각 byte 1비트 unknown
- `X^3[0..15]`: 각 byte 1비트 unknown
- `X^4[0], X^4[5], X^4[10], X^4[15]`: 각 byte 1비트 unknown
- `X^6[0], X^6[2]`: 완전 2바이트
- `X^7`: 전체 ciphertext

문제 힌트에서 가져온 핵심은 중간 표현별 후보를 미리 만들고 공유 key
byte로 join하는 관점이다. 최종 코드는 명시적인 `X^5` 역계산이나
`X^7 -> X^4` backward table을 만들지 않는다. 실제 결합은 다음과 같다.

1. `X^0/X^1`과 `X^7/X^6`의 직접식으로 `K[0]`, `K[1]`, `K[3]`을 구한다.
2. `X^3`의 1-bit-unknown 16바이트를 `2^16`개 완성해 `F(X^3)`와
   `InvMC(X^3 column)`을 record로 만든다.
3. `X^4` 대각 leak를 각 record의 `F(X^3)`와 결합해
   `K[10..13]` 후보를 만든다.
4. `X^2` 첫 column의 `2^4=16` completion에서 얻은 key-byte 관계를
   `X^3` record와 join해 `K[5..9]`, `K[15]`를 고정한다.
5. 남은 `K[2]`, `K[4]`, `K[14]`는 같은 `X^2`를 전방식과
   `X^3` 역산식이 함께 만드는 조건으로 완성한다.

라운드키가 master key byte permutation으로 연결되므로 서로 다른 round의
leak가 같은 master-key byte에 즉시 제약을 건다는 점이 탐색 공간을 줄이는
핵심이다.

### 5. 구현된 전체 공격

`solutions/solve_08_aes_key.py`는 다음 단계를 모두 구현한다.

1. AES 정·역연산과 변형 key schedule 구현
2. leak bit pattern을 byte 후보 집합으로 변환
3. `X^0/X^1`, `X^7/X^6` 직접식으로 세 key byte 복원
4. `X^3`의 `2^16` completion과 `X^4` 대각 leak로 record 생성
5. `X^2` 첫 column의 16개 completion을 shared key byte 기준으로 join
6. `K[2]`, `K[4]`, `K[14]`를 채워 leak pair에서 유일 key 확정
7. 복원한 key로 50,000개 평문/암문 pair 전체 재암호화

`complete_partial_keys()`는 한 partial key에서 일관된 첫 조합만 반환하지
않고 가능한 `(K[2], K[4], K[14])`를 끝까지 생성한다. 생성된 full key는
`set[bytes]`에 모아 서로 다른 경로에서 같은 key가 나오는 경우를
중복 제거한다. leak pair의 ciphertext까지 만족하는 서로 다른 key가 정확히
하나임을 확인한 뒤에만 결과를 반환한다.

### 6. 탐색량과 측정

핵심 탐색량은 다음과 같다.

| 단계 | 후보 또는 작업 수 |
| --- | ---: |
| `X^3`의 1-bit unknown 16개 completion | `2^16 = 65,536` |
| `X^2[0..3]`의 1-bit unknown completion | `2^4 = 16` |
| 기본 `X^2`/`K[10]` relation | `16 × 32 = 512` |
| `X^2` completion과 `X^3` record 비교 | `2^20 = 1,048,576` |
| 최종 사후 검증 | 50,000 block × 7 rounds |

메모리의 주된 항은 `x3_records`의 65,536개 tuple이다. 각 record에는
`X^3`, 필요한 네 `InvMC` column, 네 개의 `F(X^3)` 대각 byte만 저장한다.
현재 Python object 표현에서는 이 테이블 때문에 공간 복잡도가
`O(2^16)`이다. packed integer나 고정폭 array로 바꾸면 상수 계수를 더
줄일 수 있지만, 정답 복원에는 필요하지 않았다.

다음 wrapper는 key 탐색, exhaustive completion, 50,000쌍 검증을 포함한
wall time과 Linux peak RSS를 같은 process에서 잰다.

```bash
python3 - <<'PY'
import platform
import resource
import runpy
import time

print(f"python = {platform.python_version()}")
print(f"platform = {platform.platform()}")
started = time.perf_counter()
runpy.run_path("solutions/solve_08_aes_key.py", run_name="__main__")
print(f"elapsed_seconds = {time.perf_counter() - started:.3f}")
print(f"max_rss_kib = {resource.getrusage(resource.RUSAGE_SELF).ru_maxrss}")
PY
```

측정 환경은 Python 3.11.2,
Linux 6.1.0-51-cloud-amd64(glibc 2.36)였고 두 실행은
41.706~57.160초, 59,812~60,436 KiB(약 58.4~59.0 MiB)였다.
시간과 RSS는 Python·allocator·CPU에 따라
달라질 수 있으므로 공격 복잡도의 증명값이 아니라 이 구현의 재현 가능한
실측치로만 제시한다.

## 결과

최종 스크립트는 다음을 검증한다.

- 0-based index `28178`의 pair가 leak의 `X^0`, `X^7`과 일치한다.
- 표준 AES state layout 가정에서 `K[0]=0x29`, `K[1]=0x23`, `K[3]=0x84`가 나온다.
- `X^3 -> X^4` 대각 leak로 `K[10]`, `K[11]`, `K[12]`, `K[13]` 후보 집합을 만든다.
- `X^2` column leak와 `K[3]`, `K[10]` 후보를 결합해 512개 relation으로 줄인다.
- `solve_08_aes_key.py`는 각 partial key에서 가능한 `K[2]`, `K[4]`, `K[14]`를
  모두 생성하고, 중복 제거 뒤 leak pair를 만족하는 서로 다른 key가 하나임을 확인한다.
- 복구한 key로 50,000개 평문/암문 pair 전체를 재암호화해 mismatch 0개를 확인했다.
- 최종 key가 `submissions/08/master_key.txt`와 byte-for-byte 일치하는지 확인한다.

탐색 메모로는 `/tmp` 가상환경의 `z3-solver`로 full AES bit-vector 모델과
state/key-layout 변형도 짧게 시도했으나 모두 timeout에 해당하는 `unknown`으로
끝났다. 이 일회성 probe의 코드와 정확한 timeout 기록은 보존하지 않았으므로
재현 가능한 실패나 SMT 접근의 부정적 근거로 사용하지 않는다. 최종 경로는
위 leak 기반 후보-join 구현이 실제 key를 찾고 전체 50,000쌍을 검증했다는
양성 결과를 기준으로 선택했다.

따라서 8번은 master key 복구 및 전체 데이터 검증까지 완료다.

## 참고 자료와 활용

- [NIST FIPS 197-upd1, *Advanced Encryption Standard (AES)*](https://doi.org/10.6028/NIST.FIPS.197-upd1) — `AES state layout`과 구현 전반에서 사용한 column-major state 표현, SubBytes, ShiftRows, MixColumns 및 각 역변환의 정의를 확인하는 기준이다.
- [Hüseyin Demirci and Ali Aydın Selçuk, *A Meet-in-the-Middle Attack on 8-Round AES* (FSE 2008)](https://www.iacr.org/archive/fse2008/50860106/50860106.pdf) — `문제 힌트와 실제 공격의 관계`에서 원래 공격과 이 풀이의 범위를 구분하고, 중간 표현의 precompute/join 관점만 참고했다. 최종 solver는 문제의 state leak와 key permutation을 이용한 후보 join이며, 논문의 5라운드 distinguisher나 다라운드 후방 경로를 구현하지 않았다.
