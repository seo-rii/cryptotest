# 8. 블록암호 - 변형 AES 7라운드

## 문제

`plaintext.bin`과 `ciphertext.bin`에는 동일한 master key로 암호화한 50,000개 평문/암문 쌍이 들어 있다. 암호는 변형된 7라운드 AES다.

라운드 구조:

```text
X^0 = P
for i = 0..6:
    Y^i = SB(X^i)
    Z^i = SR(Y^i)
    W^i = MC(Z^i)
    X^{i+1} = W^i xor k_i
C = X^7
```

표준 AES와 달리 초기 AddRoundKey가 없고, 마지막 라운드에도 MixColumns가 있다. 라운드키는 master key byte의 permutation과 일부 `MC` 적용으로 만들어진다.

`leaked.txt`에는 28,178번째 평문의 일부 중간 state bit가 기록되어 있다. 목표는 16바이트 master key를 복원하는 것이다.

## 배경지식

### AES state layout

AES는 16바이트 state를 4x4 matrix로 보며, 표준 구현에서는 column-major layout을 사용한다.

```text
state index = row + 4*column
```

SubBytes는 byte별 S-box, ShiftRows는 row별 rotate, MixColumns는 column별 GF(2^8) 선형 변환이다.

### Demirci-Selcuk Meet-in-the-Middle

힌트의 Demirci-Selcuk MITM은 AES reduced-round 공격 계열이다. 핵심은 여러 라운드의 활성 byte 구조를 이용해 앞쪽 라운드에서 가능한 중간값 집합과 뒤쪽 라운드에서 가능한 중간값 집합을 만들고, 중간에서 만나는 후보만 남기는 것이다.

이 문제에서는 다음 정보가 공격에 쓰인다.

- 많은 known plaintext/ciphertext pair
- 특정 pair의 여러 라운드 중간 state bit leak
- 라운드키가 master key의 단순 permutation/MC로 만들어지는 구조

## 풀이 접근

### 1. leak index 검증

문제는 28,178번째 pair의 중간값이 leak되었다고 한다. 파일에서 해당 pair를 읽으면 다음과 같다.

```text
P[28178] = b3a6db3c870c3e99245e0d1c06b747de
C[28178] = 0b764cbfd5a347a13b41b4fdd5b11e00
```

이는 `leaked.txt`의 `X^0`과 `X^7` 전체 byte와 일치한다.

### 2. 직접 복원되는 key byte

표준 AES column-major layout을 가정하면 첫 라운드에서

```text
X^1 = MC(SR(SB(X^0))) xor k0
```

이다. `leaked.txt`에는 `X^1[0] = 0x20`이 완전히 주어져 있다. 따라서

```text
k0[0] = MC(SR(SB(X^0)))[0] xor X^1[0]
```

계산 결과:

```text
K[0] = 0x29
```

문제의 key schedule 정의상 `k0`는 master key `K` 자체이므로 master key 첫 byte도 `0x29`다.

마지막 라운드 쪽에서도 직접 복원되는 byte가 있다. 문제의 key schedule에서

```text
k6 = MC(K[1], K[5], K[7], K[14], K[15], K[8], K[0], K[4], ...)
```

이고 `X^7 = MC(SR(SB(X^6))) xor k6`이다. ciphertext column에 `InvMC`를 적용하면 key schedule의 `MC`가 선형성으로 풀린다.

```text
InvMC(C column 0) xor [K1, K5, K7, K14] = SR(SB(X^6)) column 0
InvMC(C column 2) xor [K9, K13, K3, K6] = SR(SB(X^6)) column 2
```

`X^6[0]`, `X^6[2]`가 완전히 leaked 되었으므로 다음이 나온다.

```text
K[1] = 0x23
K[3] = 0x84
```

### 3. 후보 집합 축소

`X^3 -> X^4`의 대각선 leak는 네 개의 독립된 4-byte group으로 나뉜다. `k3`는 master key permutation만 적용된 round key이므로 다음 후보 집합을 얻었다.

```text
K[10] candidates (32)
K[11] candidates (16)
K[12] candidates (32)
K[13] candidates (32)
```

또한 `X^2[0..3]`는 16개의 column 후보뿐이다. `MC`의 선형성을 이용하면

```text
InvMC(X^2 column 0) = SB(X^1 diagonal) xor [K5, K8, K6, K3]
```

이고, 이미 구한 `K[3]=0x84` 및 `K[10]` 후보와 결합해 다음 compact relation으로 줄어든다.

```text
combined X^2/K[3]/K[10] relation candidates = 512
unique K[5] candidates  = 16
unique K[8] candidates  = 16
unique K[15] candidates = 16
unique K[6] candidates  = 192
```

이 후보들은 다시 `X^3 = F(X^2) xor k2`를 거꾸로 풀 때 쓰인다. `k2` column 0은 이미 알려진 key byte만 포함하므로 `InvF(X^3 xor k2)`의 세 byte가 `K[2]`, `K[4]`, `K[14]`를 순차적으로 고정한다.

최종 복구된 master key:

```text
K = 2923be84e16cd6ae529049f1f1bbe9eb
```

### 4. 전체 key 복원 방향

현재 leak 구조:

- `X^1[0]`: 완전 1바이트
- `X^2[0..3]`: 각 byte 1비트 unknown
- `X^3[0..15]`: 각 byte 1비트 unknown
- `X^4[0], X^4[5], X^4[10], X^4[15]`: 각 byte 1비트 unknown
- `X^6[0], X^6[2]`: 완전 2바이트
- `X^7`: 전체 ciphertext

전방으로는 `X^0 -> X^1 -> X^2 -> X^3` 제약을 만들고, 후방으로는 `X^7 -> X^6 -> X^5 -> X^4` 제약을 만든다. 중간의 diagonal/column 단위 표현에서 후보 key byte 조합을 meet해야 한다.

라운드키가 master key byte permutation으로 연결되기 때문에, 한 라운드에서 찾은 key byte 후보는 다른 라운드 key byte 후보와 즉시 제약을 공유한다. 이 점이 탐색 공간을 줄이는 핵심이다.

### 5. 구현해야 할 전체 공격 골격

완전 풀이 구현은 다음 단계를 따른다.

1. AES inverse operations 구현: InvMC, InvSR, InvSB
2. key schedule permutation을 master key byte index dependency graph로 정리
3. leak bit pattern을 byte 후보 집합으로 변환
4. 전방 후보 생성: `X^1`, `X^2`, `X^3` leak 만족
5. 후방 후보 생성: `X^7`, `X^6`, `X^4` leak 만족
6. shared master key byte 기준으로 meet
7. 남은 후보를 50,000개 평문/암문 pair 일부로 검증

## 현재 결과

현재 스크립트는 다음을 검증한다.

- 28,178번째 pair가 leak의 `X^0`, `X^7`과 일치한다.
- 표준 AES state layout 가정에서 `K[0]=0x29`, `K[1]=0x23`, `K[3]=0x84`가 나온다.
- `X^3 -> X^4` 대각 leak로 `K[10]`, `K[11]`, `K[12]`, `K[13]` 후보 집합을 만든다.
- `X^2` column leak와 `K[3]`, `K[10]` 후보를 결합해 512개 relation으로 줄인다.
- `solve_08_aes_key.py`는 512개 partial key에서 `K[2]`, `K[4]`, `K[14]`를 복원하고 전체 key를 찾는다.
- 복구한 key로 50,000개 평문/암문 pair 전체를 재암호화해 mismatch 0개를 확인했다.

추가로 `z3-solver`를 `/tmp` 가상환경에 설치해 full AES bit-vector 모델도 시도했다. standard column-major, row-major, key schedule MC layout 변형을 각각 짧은 타임아웃으로 돌렸지만 모두 `unknown`이었다. 즉 일괄 SMT 풀이보다는 문제 힌트의 Demirci-Selcuk MITM 구조로 후보를 명시적으로 join하는 방향이 맞다.

따라서 8번은 master key 복구 및 전체 데이터 검증까지 완료다.
