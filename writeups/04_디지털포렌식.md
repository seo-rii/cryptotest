# 4. 디지털포렌식 — SafeTensors low-nibble steganography

## 결과와 재현 범위

최종 플래그는 다음과 같다.

```text
CRYPTO{G00D_J0B!_y0u_f0und_7h3_h1dd3n_s3cr37_1n_LLM}
```

재현 코드는 [`solve_04_digital_forensics.py`](../solutions/solve_04_digital_forensics.py)에 있다. 코드는 다음 세 작업을 서로 분리한다.

1. `server.log`를 bounded-memory로 검색하고 증거를 남긴다.
2. SafeTensors의 **모든 F32 tensor**를 chunk 단위로 조사해 이상 후보를 찾는다.
3. 발견된 tensor와 row를 명시해 payload를 다시 추출한다.

대회 원본 모델과 약 17GB의 로그는 저장소에 포함되어 있지 않다. 따라서 이 문서에 적힌 대화와 `345`라는 수치는 기존 분석 산출물에 남은 관측값이며, 이번 정리 과정에서 원본으로 다시 측정한 값이라고 주장하지 않는다. 대신 solver가 공식 원본으로 재실행할 때 byte offset, line hash, 원문, 전체 후보 수와 tensor별 통계를 기계 판독 가능한 파일로 남기도록 했다.

## 입력 무결성

문제 PDF에 명시된 SHA-256은 다음과 같다.

| 파일 | SHA-256 |
|---|---|
| `TinyLlama-1.1B-Chat-v1.0.zip` | `144155ad4b55ecf4e14f08457d4d8874ef656ea69e29632cc55bb97057269fa7` |
| `server.zip` | `1a0ecbdcb1ed4e3e51069643690659002612fbccc5a7a27919df17b7ab49dd5c` |
| `server.log` (`server.zip` 내부) | `d7e3c1fb4c94754c80cedddbd2a6caa0fb7f2aa6a3344bcba9a25e132d1f4cd5` |

공식 파일을 저장소 루트의 다음 경로에 둔다.

```text
4_raw/
├── TinyLlama-1.1B-Chat-v1.0.zip
└── server.zip
```

`--verify-sha256`은 두 ZIP을 8MiB씩 스트리밍 해시한다. 로그 검색 중에는 압축을 푼 `server.log`의 모든 byte를 다시 해시해 내부 member digest도 검증한다. 외부 ZIP이 맞더라도 내부 로그 검증을 생략하지 않는다.

## 1단계: 로그 단서와 증거 보존

다음 명령은 로그 전체를 한 번 순차 통과한다.

```bash
python3 solutions/solve_04_digital_forensics.py \
  --model 4_raw/TinyLlama-1.1B-Chat-v1.0.zip \
  --extract \
  --scan-log 4_raw/server.zip \
  --verify-sha256 \
  --log-report log-evidence.jsonl
```

기본 후보 조건은 base64와 Caesar를 복원한 `q1` 또는 `a1`에 다음 문자열 중 하나가 대소문자 무시로 포함되는 것이다.

```text
secret, square, flag, crypto, 4 bit, nibble
```

조건은 `--log-keyword`를 반복해 바꿀 수 있다. `log-evidence.jsonl`에는 다음이 순서대로 기록된다.

- 실제 검색 문자열과 최대 line 크기
- 각 후보의 1-based line number
- 압축 해제된 `server.log` 기준 line 시작점과 regex가 잡은 record 시작점의 0-based byte offset
- newline을 포함한 정확한 line SHA-256과 record 자체의 SHA-256
- 일치한 검색어와 복호화한 질문·답변
- 사람이 읽는 raw line/record와, byte를 손실 없이 복원할 수 있는 각각의 base64
- 전체 line 수, chat record 수, 후보·제외 수, decode 오류 수
- 스트리밍 계산한 내부 `server.log` SHA-256

chat을 리스트에 누적하지 않고 후보를 찾는 즉시 콘솔과 JSONL에 기록한다. 논리 line은 기본 1MiB로 제한하며, 그보다 긴 line은 작은 조각으로 끝까지 읽어 내부 SHA-256에는 포함하되 정규식 분석에서는 제외하고 개수를 보고한다. 따라서 메모리는 17GB 입력 크기가 아니라 chunk와 최대 line 크기에 의해 제한된다.

기존 분석 기록에 남은 결정적 복호 결과는 다음과 같다.

```text
model: TinyLlama/TinyLlama-1.1B-Chat-v1.0
chat_id: chat-000005
Q: What secret does the model have?
A: The LLM knows the secret. Trust me. "square" for open seasame!!!
```

`open seasame`은 기록된 복호문에 있던 철자다. 다만 원본 로그가 이 저장소에 없으므로 여기에는 검증하지 못한 raw `q1`/`a1`, offset, line hash를 지어 넣지 않았다. 공식 원본으로 생성한 `log-evidence.jsonl`이 정확한 record의 근거가 된다.

### 로그 field의 padding 처리

각 field는 부족한 base64 문법상 `=`만 복원한 뒤 decode하고, 알파벳에 Caesar `+11`을 적용한다. 예전 추출기의 다음 처리는 삭제했다.

```python
caesar_shift(decoded).rstrip("l")
```

`rstrip("l")`은 padding 길이를 모르는 상태에서 정상 평문의 마지막 `l`까지 모두 지울 수 있다. 현재 코드는 복호된 문자를 하나도 삭제하지 않는다. 생성기 명세에서 padding 길이가 따로 확인된다면 그 **정확한 길이만** 잘라야 하며, 특정 문자를 기준으로 제거해서는 안 된다.

## 2단계: 모델 상호작용의 지위

기존 탐색 기록에는 `square`를 입력했을 때 다음 응답을 관측했다고 남아 있다.

```text
User: square
Assistant: Wouldn't about 4 bits be enough?
```

이는 low 4-bit 채널을 조사하게 한 유용한 가설이지만, 그대로는 재현 가능한 실험 증거가 아니다. 당시의 다음 값이 기록되어 있지 않기 때문이다.

| 항목 | 현재 상태 |
|---|---|
| `transformers` / `torch` 버전 | 기록 없음 |
| 정확한 tokenizer·model 경로 | TinyLlama 식별자 외 기록 없음 |
| chat template와 system prompt | 기록 없음 |
| `do_sample`, temperature, `top_p` | 기록 없음 |
| `max_new_tokens`, random seed | 기록 없음 |
| greedy decoding에서의 반복성 | 검증 기록 없음 |

따라서 이 문서는 해당 문장이 언제나 생성된다고 주장하지 않는다. 최종 검증은 LLM 출력에 의존하지 않고 SafeTensors byte를 직접 조사하고 추출하는 단계로 수행한다. 모델 대화를 다시 실험한다면 위 항목과 실제 prompt rendering 결과를 함께 보존해야 한다.

## 3단계: tensor anomaly blind discovery

위 단서로 float32의 little-endian 최하위 byte에 있는 low nibble을 조사한다. TinyLlama 가중치는 F32로 저장되어 있지만 최하위 bit가 거의 모두 0인 tensor가 많아, 비영 low nibble은 강한 이상치가 된다.

기존 분석은 다음 결과를 기록했다.

```text
model.embed_tokens.weight: low nibble non-zero count = 345
다른 tensor: 유의미한 연속 ASCII 후보 없음
```

이제 solver가 그 발견 과정을 직접 수행한다.

```bash
python3 solutions/solve_04_digital_forensics.py \
  --model 4_raw/TinyLlama-1.1B-Chat-v1.0.zip \
  --discover \
  --verify-sha256 \
  --discovery-report discovery.json
```

`--discovery-report discovery.csv`처럼 확장자를 바꾸면 CSV로도 저장한다. 각 F32 tensor에 대해 다음 값을 기록한다.

| 필드 | 의미 |
|---|---|
| `dtype`, `shape`, `data_start`, `data_end` | tensor 종류와 SafeTensors data buffer 상대 범위 |
| `low_nibble_nonzero_count/ratio` | 각 F32의 byte 0 low nibble이 0이 아닌 수와 비율 |
| `first/last_nonzero_element` | 이상 구간의 element 경계 |
| `longest_nonzero_run` | 연속된 비영 nibble의 최장 길이 |
| `candidate_span_bytes` | 첫 비영 nibble-pair부터 마지막 비영 pair까지의 byte 구간 |
| `candidate_ascii_score` | 그 구간에서 printable ASCII 또는 `TAB/LF/CR`인 byte의 비율 |
| `candidate_preview_*` | 최대 192-byte의 escaped/hex preview |

스캔은 tensor 전체를 메모리에 올리지 않고 8MiB chunk만 유지한다. 각 F32의 little-endian byte 0만 뽑아 nibble 두 개를 `(high << 4) | low`로 결합한다. stdout 순위는 ASCII score, 비영 nibble 수, span 길이 순이며 JSON/CSV에는 순위와 관계없이 모든 F32 tensor 결과가 들어간다.

### SafeTensors 경계 검증

헤더를 신뢰한 채 임의 위치로 이동하지 않는다. 데이터를 읽기 전에 다음을 모두 확인한다.

1. 8-byte little-endian header 길이가 파일/member 범위와 reference implementation의 100,000,000-byte 한계 안에 있다.
2. header가 `{`로 시작하고 JSON 뒤 padding은 ASCII space만 사용하며 duplicate key가 없다.
3. `__metadata__`는 string-to-string map이고, dtype과 shape의 각 차원이 유효하다.
4. `0 <= start <= end <= data_buffer_size`다.
5. `(end - start) * 8 == product(shape) * dtype_bits`이고 sub-byte dtype도 byte boundary에 맞는다.
6. 정렬한 모든 tensor range가 겹치거나 빈 구간 없이 data buffer 전체를 정확히 덮는다.
7. 추출할 row가 tensor의 `end`를 넘지 않는다.

SafeTensors의 `data_offsets`는 파일 절대 offset이 아니라 JSON header 직후 data buffer의 시작을 기준으로 한다. parser는 header를 다 읽은 위치에서 상대 `start`만큼 이동하므로 이 규칙과 일치한다.

## 4단계: payload 추출

discovery가 가리킨 tensor와 row를 명시해 재추출한다.

```bash
python3 solutions/solve_04_digital_forensics.py \
  --model 4_raw/TinyLlama-1.1B-Chat-v1.0.zip \
  --extract \
  --tensor model.embed_tokens.weight \
  --row 0 \
  --verify-sha256
```

절차는 다음과 같다.

1. 검증된 `model.embed_tokens.weight`의 첫 row로 이동한다.
2. 각 F32 값의 little-endian 첫 byte에서 `value & 0x0f`를 취한다.
3. nibble 두 개를 한 byte로 결합한다.
4. 복원 byte stream에서 `CRYPTO{...}`를 정규식으로 다시 확인한다.

기존 분석에서 복원한 payload는 다음과 같다.

```text
"The lighthouse opens at midnight. Meet me at the bar."

Well done, Agent H.
You traced the secBet into the model itself.
The flag is: CRYPTO{G00D_J0B!_y0u_f0und_7h3_h1dd3n_s3cr37_1n_LLM}
```

`secBet`은 기록된 payload의 철자다. solver는 PyTorch나 Transformers를 사용하지 않으며, 플래그가 실제 복원 byte에 없으면 성공으로 처리하지 않는다.

## 합성 회귀 검증

공식 대형 원본과 별개로 파서·스트리밍 로직은 작은 합성 ZIP으로 검증한다.

```bash
python3 -m unittest -v solutions.test_solve_04_digital_forensics
```

테스트는 ZIP 내부 SafeTensors discovery/extract 왕복, nibble pair와 비영 run의 chunk 경계, empty tensor와 scalar, header padding·duplicate key·hole·overlap·미정렬 sub-byte 거부, 긴 로그 line의 bounded skip, line/record offset·hash·raw evidence와 UTF-8 decode 오류 집계를 확인한다. 이 검증은 공식 `chat-000005`, 비영 nibble 수 `345`, 최종 payload를 다시 측정한 것이 아니라 구현 경계 조건만 독립적으로 확인한다.

## 제출물과 남은 외부 검증

[`../submissions/04/`](../submissions/04/)에는 실행 가능한 `solve.py`, 방법론 문서 원본 `report.md`, 렌더링한 `report.pdf`, `flag.txt`를 직접 넣었다. 모델과 로그는 문제에서 따로 배포하는 대형 입력이므로 포함하지 않는다.

저장소에 없는 공식 원본이 확보되면 최종 제출 전에 다음 두 산출물을 한 번 더 보존해야 한다.

```text
log-evidence.jsonl   # 실제 decisive record offset/hash/raw와 전체 검색 집계
discovery.json       # 실제 모든 F32 tensor 통계
```

이 두 파일이 있어야 기존 분석 기록의 `chat-000005`, `345`와 payload를 제3자가 blind discovery부터 독립 검증할 수 있다.
