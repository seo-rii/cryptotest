# 2. 암호구현 - 256비트 permutation 복원과 성능 최적화

## 문제와 제출 목표

상태는 네 개의 64비트 word이고 한 라운드는 다음 네 종류의 연산을 한
번씩 사용한다.

- word별 rotate-left
- 네 word와 상수의 XOR
- 32바이트 permutation
- word별 modulo `2^64` 덧셈

1라운드의 순서와 서로 다른 rotation 네 개를 복원하고, 같은 함수를
20라운드 반복해야 한다. 정확성 30점과 문서 30점은 절대평가지만 성능
40점은 상대평가이므로, 정답을 찾은 뒤 실제 제출 harness의 한 상태
직렬 workload를 최적화해야 한다.

최종 결과는 다음과 같다.

```text
round = rotate -> XOR -> reverse all 32 bytes -> add
rot   = {43, 7, 29, 14}
```

## 1. 구조와 rotation 복원

각 단계는 역연산이 있다.

- 덧셈은 같은 상수를 빼면 된다.
- `shuffle_map[i]=31-i`인 32바이트 reversal은 자기 자신의 역이다.
- XOR은 같은 상수를 다시 XOR하면 된다.
- rotate 값은 허용 범위 `1..63`을 모두 검사할 수 있다.

출력 `out`에 역연산을 적용한다.

```text
t0 = out - constants1              (word별 mod 2^64)
t1 = reverse_all_32_bytes(t0)
t2 = t1 XOR constants2
```

각 word `i`에서 `ROTL64(input[i],r_i)==t2[i]`인 `r_i`를 찾는다.
`solutions/solve_02_permutation.py`는 첫 벡터 하나에 의존하지 않고 제공된
1,000개 벡터에서 후보 집합을 모두 교차한다. 각 word에 정확히 하나씩
`43,7,29,14`가 남고, forward evaluation이 모든 벡터와 일치한다.

## 2. 기준 구현과 1차 특수화

기준 구현은 제공된 네 함수를 복원한 순서로 호출한다.

```c
rotate_words_left_64wise(state, rot);
xor_constants_256wise(state, constants2);
shuffle_bytes_256(state, shuffle_map);
add_constants_64wise(state, constants1);
```

하지만 고정 map은 임의 permutation이 아니라 전체 byte reversal이다.

```text
reverse32(x0,x1,x2,x3)
 = (BSWAP64(x3), BSWAP64(x2), BSWAP64(x1), BSWAP64(x0))
```

따라서 32회의 indexed byte copy와 임시 배열 두 개를 네 번의
`BSWAP64`로 바꿀 수 있다. 한 라운드는 다음 네 식이 된다.

```text
y0 = BSWAP64(ROTL64(x3,14) XOR C2[3]) + C1[0]
y1 = BSWAP64(ROTL64(x2,29) XOR C2[2]) + C1[1]
y2 = BSWAP64(ROTL64(x1, 7) XOR C2[1]) + C1[2]
y3 = BSWAP64(ROTL64(x0,43) XOR C2[0]) + C1[3]
```

고정 rotation은 즉시값 instruction이 되고, GCC/Clang에서는
`__builtin_bswap64`가 target byte-swap instruction으로 내려간다. 이 식을
1-round state-writing helper로 만든 뒤 제공 loop에서 20번 부르는 형태가
최적화 전 제출이었다. 상태를 20라운드 내내 register에 유지하는 loop는 이후
비교 기준으로 사용했다.

## 3. 두 라운드 합성과 최종 구현

한 라운드는 word 순서를 뒤집는다. 두 라운드를 묶으면 이 reversal이
상쇄되어 각 출력 word가 같은 위치의 원래 word에만 의존한다. source
word `j`에 rotate, XOR, byte-swap, destination add를 적용하는 함수를
`T_j`라 쓰면 두 라운드는 다음 네 독립 chain이다.

```text
x0 <- T3(T0(x0))
x1 <- T2(T1(x1))
x2 <- T1(T2(x2))
x3 <- T0(T3(x3))
```

이 식은 round마다 `x0..x3`를 서로 교환하는 형태보다 compiler가 네
독립 dependency chain을 보기 쉽다. 최종 helper는 이 2-round block을
10번 완전히 전개해 loop branch를 없앤다.

평가 CPU가 고정되어 있으므로 helper에 GCC `target("bmi2")`를 국소
지정했다. GCC가 constant rotate를 non-destructive `RORX`로 선택할 수
있고, 이 instruction은 condition flag도 변경하지 않는다. 전체 파일은
문제에서 제공한 기본 명령 그대로 컴파일된다.

최종 source는 compile-time `__BMI2__`에 따라 속성을 바꾼다. 기본
`gcc -O3`에서는 위의 국소 BMI2 noinline helper를 유지한다. 성능 점수용으로
`-mbmi2 -finline-limit=2000`을 주면 helper가 public 20-round 함수에,
그 함수가 다시 `main`의 timing loop에 들어간다. permutation 식은 같지만
outer call마다 반복되던 함수 prologue/epilogue와 상태·상수 memory traffic이
없어지고, state와 상수가 호출 사이에도 register에 남는다.

문제의 수정 범위에는 외부 helper 추가가 허용된다. 제공된 20-round
`for`문의 허용된 line에서 helper가 20라운드를 한 번에 수행하고 `r=19`로
남은 중복 iteration을 끝낸다. 함수는 임의 상태에 같은 permutation을
적용하며 benchmark input이나 정답 상태를 하드코딩하지 않는다.

## 4. 여러 최적화 후보 비교

`solutions/02_optimization/benchmark_02_candidates.c`에는 같은 reference를
공유하는 후보 여덟 개가 있다. 각 후보는 별도 binary로 컴파일해 큰
unrolled function끼리 instruction-cache layout에 영향을 주지 않게 했다.
모든 후보가 제공 벡터와 100,000개 random differential case를 통과한 뒤
warm-up과 반복 측정을 수행한다.

AMD EPYC 7B12, GCC 12.2.0, `-O3 -march=native`, CPU 2 고정,
2,000,000-call 표본 15개의 후보 선별 결과는 다음과 같다.

| 후보 | 중앙값 ns/20-round | MAD ns | 최적화 전 대비 |
|---|---:|---:|---:|
| 보존된 최적화 전 제출 형태 | 41.894 | 2.834 | 1.000x |
| register loop | 40.655 | 3.083 | 1.031x |
| paired AVX2 loop | 39.718 | 0.131 | 1.055x |
| paired scalar loop | 37.751 | 2.649 | 1.110x |
| paired AVX2 full-unroll | 39.417 | 0.086 | 1.063x |
| paired scalar full-unroll | 36.824 | 2.617 | 1.138x |
| paired scalar full-unroll + BMI2 | **36.249** | 3.195 | **1.156x** |
| one-state AVX2 | 73.630 | 0.266 | 0.569x |

이 표는 후보 선별용 steady microbenchmark다. 실제 제출에서 compiler가
무엇을 inline하는지가 다르므로 이것만으로 최종안을 정하지 않았다.

### 성능이 나빠진/채택하지 않은 후보

한 상태를 AVX2 register 하나에 넣는 방법은 네 lane rotate를 위해
variable left/right shift와 OR가 필요하고, 이어 XOR, byte shuffle,
128-bit-half permutation, add가 하나의 긴 직렬 chain을 이룬다. 네 scalar
word의 짧은 chain 네 개보다 느려 73.630ns가 나왔으므로 제외했다.

네 상태를 lane별로 transpose한 batch-4 AVX2는 throughput은 좋아졌지만
공식 API와 timing loop가 상태 하나를 직렬 갱신하므로 제출에 쓸 수 없다.
이는 다른 workload에는 유효한 최적화지만 이 문제의 score metric과
다르다.

compiler가 두 라운드 식을 AVX2로 SLP vectorize한 paired loop는 표본이
매우 안정적이었지만 이 AMD host에서는 BMI2 scalar보다 느렸다. target
Intel에서는 execution-port와 latency balance가 다를 수 있다는 이유로 처음에는
재측정 후보로 남겼다. 그러나 뒤의 18-candidate 심층 검토에서 loop와 unroll이
각각 0.9566x, 0.9076x에 그쳐 최종 A/B 목록에서는 제외했다.

BMI2 없는 inline scalar full-unroll도 제출형 별도 후보로 측정해
34.748ns를 얻었고 BMI2의 34.669ns와 거의 같았다. 현재 제출은 local
winner인 BMI2를 선택했지만, 작은 차이는 target 재측정 대상이다.

두 번째 탐색에서는 BSWAP/XOR 순서 교환과 XOR 최상위 bit의 ADD 흡수,
역위상 transform의 켤레관계를 이용한 2-lane SIMD, 8/16-bit lookup table,
수동 BMI2 assembly, GCC scheduling/IRA/PGO/LTO flag를 각각 시험했다.
모두 reference와 differential test를 통과했지만 core를 대체할 반복 가능한
승자는 없었다. 특히 켤레 SIMD는 instruction 수를 줄이고도 독립 chain을
네 개에서 두 개로 줄여 약 `0.845x`로 느렸고, pre-swapped 상수의 초기
`1.095x--1.116x` 결과는 함수 배치를 뒤집은 동일-process 측정에서
`1.0146x/0.9943x`로 사라졌다. 구체적인 반증과 수치는 7절에 정리한다.

## 6. 제출 형태 반복 benchmark

기존 benchmark는 `optimized_20_rounds`를 매 outer iteration마다
`NOINLINE` 호출했지만, 이전 실제 `contest.c`는 GCC가 helper와 20-round를
`main`의 timing loop 안으로 inline했다. 이 차이는 수 ns급 후보를
판정할 때 무시할 수 없다. 또한 `median(before)/median(after)`와 각
round의 speedup 중앙값은 실제 측정에서 약 4% 달라진 적이 있다.

새 `solutions/benchmark_02_permutation.py`는 score-facing 검사를 다음처럼
수행한다.

- 최적화 전 `contest.c`를 `contest_before.c`로 보존하고 최종 제출과
  각각 별도 complete binary로 컴파일한다.
- compiler 구조를 유지한 채 timing-loop iteration만 길게 바꾼다.
- 3개 warm-up process를 버리고 기본 21개 표본을 측정한다.
- 한 logical CPU에 고정하고 case 순서를 cyclic rotation/reversal한다.
- 매 표본에서 공식 1,000/20-round vector를 검사한다.
- raw internal `clock()`와 외부 wall time, median, MAD, p05/p95, bootstrap
  median 95% interval, paired speedup을 JSON으로 남긴다.
- outlier를 지우지 않고 3-MAD flag만 표시한다.

10,000,000-call, warm-up 3회, measured 15회 캠페인 결과:

| 제출형 구현 | 중앙값 | MAD | p05--p95 |
|---|---:|---:|---:|
| 이전 scalar | 36.799 ns | 0.924 ns | 35.766--45.773 ns |
| 2-round unroll + BMI2 | 34.669 ns | 2.232 ns | 32.384--46.657 ns |

같은 measurement round끼리 계산한 speedup 중앙값은 **1.068x**, MAD는
0.045x, bootstrap 95% interval은 1.008x--1.105x였다. 그러나 shared VM의
다른 20,000,000-call 캠페인은 1.019x와 0.991x--1.082x interval을 냈다.
이 측정은 최적화 전 source와 full-unroll source를 비교한 역사적 결과다.

### 동일 source의 교차 호출 인라이닝

이번에는 최종 `contest.c` 하나를 두 번 컴파일해 source 차이와 layout이라는
교란을 없앴다. 기본 case에는 추가 flag를 주지 않고, score case에만
`-mbmi2 -finline-limit=2000`을 주었다. 3,000,000-call, warm-up process 3회,
21 samples의 독립된 두 affinity 캠페인 결과는 다음과 같다.

| affinity | 기본 중앙값 | score build 중앙값 | paired 중앙값 | paired MAD | bootstrap 95% CI |
|---:|---:|---:|---:|---:|---:|
| CPU 0 | 44.467 ns | 39.859 ns | **1.115553x** | 0.028078x | 1.109511--1.143275x |
| CPU 4 | 45.924 ns | 40.801 ns | **1.118038x** | 0.032230x | 1.094566--1.140443x |

원시는 [`inline_results_02.json`](../solutions/02_optimization/inline_results_02.json),
[`inline_results_02_cpu4.json`](../solutions/02_optimization/inline_results_02_cpu4.json)에
있다. 현재 schema 5 runner는 각 `contest.c`의 `main`만 rename해 candidate object를
만든 뒤 독립 verifier에 link한다. 공식 vector는 모든 timing process에서,
무작위 상태와 무작위 ADD/XOR 상수 100,000건의 1/20라운드는 각 candidate의
public 함수를 직접 호출해 timing 전에 검증한다. `--audit-mode`를 지정한 case는
실제로 timing할 complete executable의 loop를 해당 assembly contract로
감사한다. 이 writeup의 권장 명령은 모든 case에 mode를 지정하므로 정확성을
검사한 object와 성능 binary가 달라지는 공백도 막는다. 또한 실제
timing `main`의 모든 warm-up/sample이 선언한 반복 횟수와 독립 oracle의
최종 256-bit state를 출력해야 한다. current protocol은 total-derived timing,
출력 average 일치, child-CPU coverage와 nonce-derived alternate iteration도
검사하고 raw sample에서 four-block stationarity를 독립 재계산한다. 이 field와
protocol hash 전의 schema-5 timing도 새 confirmation에는 섞지 않는다. 과거
schema 2의
`random_differential_cases`는 oracle 자체 검사였으므로 alignment/codegen
및 stages JSON은 공식-vector gate가 있는 성능 기록으로만 해석하고, 기존 inline/ROL
schema 3 JSON은 candidate 직접 검증까지 포함한 역사적 기록으로 구분한다.

`기본 / -mbmi2만 / outer inline`의 3단계 ablation에서는 paired
`1.000x / 0.999x / 1.124x`였다. 즉 BMI2 core 자체가 아니라 public 함수와
`main` 사이 경계를 없애야 이득이 생긴다는 assembly 분석과 일치한다.
해당 raw 결과는
[`inline_stages_results_02.json`](../solutions/02_optimization/inline_stages_results_02.json)에
남겼다.

GCC 12에서 inline limit 700과 2000은 byte-identical binary를 만들었고,
별도 limit-700 캠페인도 paired `1.122x`, 95% CI
`1.100x--1.143x`였다. 이후 digest로 고정한 공식 GCC 13.3.0에서도 두 limit의
complete binary가 동일함을 확인했다. 둘 다 1,216-byte/322-instruction timing
loop를 만들며 `call permute_20rounds`가 없다. 따라서 255H에서 남은 불확실성은
인라인 성공 여부가 아니라 서로 다른 backend schedule의 실제 순위다.

수작업 확인을 놓치지 않도록
[`audit_inline_02.py`](../solutions/02_optimization/audit_inline_02.py)를 추가했다.
GCC 12에서 limit 700/2000의 normalized loop hash는 같았다. score loop는
1,216 bytes/322 instructions이고 `RORX/XOR/BSWAP/ADD-or-LEA`가 각각 80개,
core 밖 call·push/pop·상태/상수 memory operand가 모두 0이다. 기본 loop는
19 bytes/6 instructions와 helper call 하나다. 전체 결과는
[`inline_assembly_audit_02.json`](../solutions/02_optimization/inline_assembly_audit_02.json)에

## 7. 알고리즘과 cache/micro 최적화 심층 재검토

초기 후보 선별 뒤에도 [별도 심층 실험](../solutions/02_optimization/deep_review_02.md)을
진행했다. 18개 후보를 각각 독립 binary로 만들고 공식 1-round 1,000개,
20-round vector, 무작위 differential 100,000개를 다시 통과시킨 뒤 paired
측정을 수행했다. 전체 raw sample은
[`deep_results_02.txt`](../solutions/02_optimization/deep_results_02.txt)에 남겼다.

### 알고리즘 관점

두 라운드 합성 뒤 각 64비트 word는 서로 독립이지만, 각 word 내부에는
라운드마다 `RORX -> XOR -> BSWAP -> ADD`라는 직렬 경로가 남는다. modulo
덧셈의 carry 때문에 이 합성은 더 작은 rotate/XOR/add 형태로 닫히지 않는다.
word `i`의 한 라운드 변환을 `T_i`라 쓰면 정확한 합성은 다음과 같다.

```text
R^2(x)_i = T_(3-i)(T_i(x_i))
R^20     = (R^2)^10
```

이를 일반 함수의 거듭제곱처럼 exponentiation-by-squaring으로 줄이려면 합성
결과를 같은 작은 표현으로 보존해야 하지만, ADD의 carry 때문에 불가능했다.
일반 64비트 합성 함수를 table로 만들면 사실상 `2^64` mapping이 필요하다.

항상 byte-swapped 상태 `z=BSWAP64(x)`를 유지하는 표현도 시험했다. 이때
덧셈은 `z'=BSWAP64(BSWAP64(z)+A)`가 되어 두 번의 변환과 반대 방향 carry를
다시 처리해야 한다. rotation `43/7/29/14`도 byte 경계가 아니어서 byte table은
인접 byte의 비트와 carry 상태까지 가져야 했다. 결국 현재 instruction chain보다
짧아지지 않았다. 네 chain을 하나씩 직렬 계산한 대조군은 기준의 0.7305배
성능에 그쳐, 네 chain을 interleave해 instruction-level parallelism을 노출하는
현재 구성이 중요함을 확인했다.

### frontend, instruction/cache 관점

기본 build의 BMI2 full-unroll helper는 1,267바이트다. 함수 진입에는 callee-saved
register push 네 개가 있지만 hot body에는 spill이
없고, 상수 8개와 상태 4개가 register에 남는다. 네 chain 각각의 핵심
dependency depth는 20라운드 x 약 4개 instruction, 즉 약 80단계다. 2.25GHz
VM에서 34--36ns는 약 77--81 cycle이므로 단순 latency 하한과 거의 같다.
남은 차이는 연산 수보다 instruction frontend, decoded-uop/code layout과 target
Intel의 latency 차이에 민감하다.

score build에서는 이 1,267바이트 core가 `main`의 timing loop에 직접 들어간다.
그 loop에는 core 밖의 call, push/pop과 상태·상수 memory access가 없었다.
기본/public/core 세 함수 중 public ABI용 사본은 남아도 실제 timing 경로가
호출하지 않으므로, 단순 helper microbenchmark보다 complete binary의 `main`
assembly가 최종 판단 기준이다.

### BSWAP--XOR 교환과 수동 scheduling

`B`를 byte swap이라 하면 `B(u xor K)=B(u) xor B(K)`이므로 transform을
`RORX -> BSWAP -> XOR -> ADD` 순서로 바꿀 수 있다. 더 나아가
`H=2^63`에 대해 `z xor H = z + H (mod 2^64)`이므로 swapped XOR 상수의
최상위 bit는 add 상수에 흡수된다. 다른 bit는 carry 때문에 같은 방식으로
흡수되지 않는다. 이 항등식은 무작위 100,000건을 통과했지만 instruction
수는 그대로였다.

별도 process 측정에서는 이 후보가 `1.095x--1.116x`처럼 보였으나,
동일 process에서 AB/BA thread CPU time을 쓰고 함수 배치를 두 방향으로
바꾸자 `1.0146x`와 `0.9943x`가 됐다. 직접 쓴 inline assembly도 `0.9975x`였다.
따라서 이는 대수적 개선이 아니라 shared VM descheduling과 code layout의
착시로 판정했다.

### XOR/ADD 합치기와 두 라운드 선형부의 완전탐색

교환한 transform을 `F(x)=(L(x) xor C)+A`, `C=BSWAP(K)`로 놓고

```text
(x xor C) + A = (x + B) xor E  (mod 2^64)
```

가 되는 상수 `(B,E)`가 있는지 실제 네 `(C,A)`에 대해 조사했다. 64비트
항등식은 모든 `mod 2^n` 사영에서도 성립해야 하는데, 각각 5/3/10/4비트
완전탐색에서 이미 해가 없었다. 그러므로 XOR을 ADD 뒤로 옮겨 다음 상수와
합치는 이 구체적 3-op 축약은 불가능하다. `2^63` bit만 ADD에 흡수할 수 있는
두 상수도 나머지 XOR mask가 0이 아니어서 instruction 수는 줄지 않는다.

두 라운드의 선형 bit permutation `B R_s B R_r`도 64개 bit에서 직접 합성했다.
어느 pair도 단일 rotate, `BSWAP(ROL(x))`, `ROL(BSWAP(x))`와 같지 않았다.
43/14 계열의 cycle은 64 하나, 7/29 계열은 16 네 개다. 재현 코드는
[`analyze_transform_lower_bound_02.py`](../solutions/02_optimization/analyze_transform_lower_bound_02.py)다.
구조화된 출력은
[`transform_lower_bound_02.json`](../solutions/02_optimization/transform_lower_bound_02.json)에
보존했다. 이는 모든 회로에 대한 일반 하한은 아니지만, 이번에 고려한 상수 이동과 단일
선형 instruction 합성은 완전히 반증한다.

정확한 후보도 candidate 직접 100,000건 검증 뒤 장기 측정했다.

| 후보 | best 대비 paired | bootstrap 95% CI | 판단 |
|---|---:|---:|---|
| post-BSWAP XOR | 0.980x | 0.968--0.988x | 같은 320-op, 느림 |
| top-bit fold | 0.983x | 0.979--0.996x | XOR instruction이 남음 |
| `x xor c = x+c-2(x&c)` | 0.620x | 0.607--0.633x | AND/LEA/ADD 증가 |
| 32-bit halves/funnel shift | 0.251x | 0.247--0.260x | 약 4배 느림 |

### 켤레 SIMD

역위상 transform 사이의 `T3=C0 T0 C0^-1`, `T2=C1 T1 C1^-1` 관계를 이용하면
word 0/3과 1/2를 각각 2-lane vector로 묶을 수 있다. 공식 vector와 무작위
100,000건을 통과했고 핵심 instruction 수는 약 320개에서 240개로 줄었다.
그러나 scalar의 독립 chain 네 개가 vector chain 두 개로 줄고, lane rotate가
두 shift와 OR를 필요로 해 critical path가 길어졌다. 두 측정의 paired 결과가
`0.8450x`, `0.8482x`여서 제외했다.

### table 분해와 ANF

20-round unary word 함수 전체 table은 함수 하나당 128 EiB이고 켤레관계로
두 함수만 저장해도 256 EiB다. 선형 rotate/byte-swap만 8-bit chunk로 만들면
64 KiB와 transform당 8 loads, 16-bit chunk는 8 MiB와 4 loads가 필요하다.
ADD carry까지 포함한 byte별 table이 가능한지도
[`analyze_table_decomposition_02.py`](../solutions/02_optimization/analyze_table_decomposition_02.py)로
확인했다.

네 함수 모두 입력 byte--출력 byte influence가 `64/64`였고, 서로 다른 두
입력 byte의 혼합 XOR 미분은 각 1,000회 모두 0이 아니었다. modulo-additive
혼합 미분도 999/1000 또는 1000/1000이었다. 한 16차원 부분공간에서 출력
ANF 차수의 최소/중앙/최대가 `15/15/16`, degree-16 출력이 `29/64`였다.
이는 일반 회로 하한은 아니지만 byte별 독립 XOR/합 table이라는 구체적
전략을 반증하기에는 충분하다.

### 작은 ROL loop와 complete-binary flag matrix

같은 full-unroll을 portable forced-inline으로 빌드하면 80개 `RORX`가

### 5차: 독립 chain 순서와 backend layout 탐색

두 라운드 macro의 `x0..x3` 갱신은 서로 독립이므로 네 문장의 24개

보존한

중립 verifier의 임의 state/상수 100,000건 1/20-round를 통과했다.
상수/state local 선언 순서는 세 profile에서 byte-identical이었다.
전체 결과는

### 6차: 부분 언롤의 반증과 4-lane AVX2

full-unroll의 큰 frontend footprint를 다시 의심해 two-round block을
`1/2/5/10`개씩 펼친 143/278/646/1,211-byte loop를 만들었다. 모든 후보는
공식 vector와 임의 state/상수 100,000건을 통과했다. CPU 1의 첫 21-sample
screen에서는 가장 작은 loop가 `1.035x (1.007--1.043)`였지만, 즉시 warm-up
6회·6,000,000-call·32 samples로 확인하자 `1.0004x
(0.9855--1.0176)`로 사라졌다. unroll2는 처음부터 CI가 1을 가로질렀고
unroll5는 느렸다. 따라서 첫 screen은 frontend 후보를 찾는 신호였을 뿐 채택
근거가 아니며, 원시와 재확인은
[`partial_unroll_results_02_cpu1.json`](../solutions/02_optimization/partial_unroll_results_02_cpu1.json),
[`partial_loop_confirm_02_cpu1.json`](../solutions/02_optimization/partial_loop_confirm_02_cpu1.json)에
모두 남겼다.

scalar 식 자체도 더 줄일 수 있는지 별도로 확인했다. 한 stage를
`BSWAP64(ROL64(x,r) xor k)+a`로 두고 Z3 bit-vector CEGIS를 수행하자 서로 다른
stage의 길이 3 template 64개가 모두 UNSAT였다. 기존 8-operation pair에서
연산 하나를 지우고 상수를 다시 합성하는 `4×8=32`개도 UNSAT였다.
rotate/BSWAP 선형부는 길이 3 이하 구문 4,223개(서로 다른 bit permutation
632개)를 전수 검사했지만 일치가 없었다. 이는 정의한 grammar의 stage 하한과
기존 pair의 국소 irredundancy이지, 모든 x86 표현에 대한 전역 하한은 아니다.
재현 script와 전체 solver/codegen 기록은
[`analyze_two_round_superopt_02.py`](../solutions/02_optimization/analyze_two_round_superopt_02.py),
[`two_round_superopt_results_02.json`](../solutions/02_optimization/two_round_superopt_results_02.json)에
있다.

새 성능 후보는 과거 one-state SIMD와 구조가 다르다. 두 라운드 뒤 word
reversal이 상쇄되는 성질을 먼저 적용한 뒤, 남은 네 독립 chain을 YMM의 네
lane에 둔다. 열 개의 two-round block은
`VPSLLVQ/VPSRLVQ/VPOR/VPXOR/VPSHUFB/VPADDQ`를 각각 20회 실행한다. forward
constant를 tied-register identity helper로 timing loop 밖에 유지하자 exact
GCC 13.3 loop가 `124 instructions/587 B/hot load 2`에서
**`122 instructions/579 B/hot memory 0`**으로 줄었다. 이 micro 변경만 직접
비교하면 CPU 2에서 `1.0013x (0.9983--1.0039)`로 동률이었다.

최종 AVX2와 scalar incumbent의 독립 측정은 다음과 같다. 각 행은
3,000,000 calls, warm-up process 6회, 균형 순서 32 samples이며 측정 전에
공식 vector와 임의 state/상수 100,000건 및 exact-binary 감사를 수행했다.

| AMD affinity | scalar | AVX2 | paired median | 95% CI |
|---:|---:|---:|---:|---:|
| CPU 1 | 46.927 ns | 36.690 ns | **1.275x** | 1.260--1.292x |
| CPU 2 | 34.354 ns | 36.569 ns | **0.940x** | 0.923--0.950x |
| CPU 3 | 45.938 ns | 36.724 ns | **1.248x** | 1.222--1.269x |

CPU 1/3은 AVX2가 앞섰지만 CPU 2에서는 scalar가 유의하게 앞서 순위가 완전히
뒤집혔다. 같은 이름의 AMD VM에서도 affinity/frequency 조건이 일관되지 않다는
증거이므로 이 결과를 255H의 Lion Cove/Skymont로 옮길 수 없다. CPU 1/3 원시는
[`avx2_confirm_02_cpu1.json`](../solutions/02_optimization/avx2_confirm_02_cpu1.json),
[`avx2_confirm_02_cpu3.json`](../solutions/02_optimization/avx2_confirm_02_cpu3.json),
12개 constant-residency 변형·초기 affinity·SSE2 대조군은
[`simd_results_02.json`](../solutions/02_optimization/simd_results_02.json)에 있다.
SSE2는 781-instruction/4,064-byte loop와 약 `0.40x`로 기각했다.

또한 exact GCC 13.3 추가 47조합과 Clang 21의 53 target/scheduler 조합을 host
timing 없이 검사했다. GCC의 새 조합은 기존 120.06-cycle Alder proxy를 이기지
못했다. Clang Arrow Lake `ilpmax/ilpmin`은 1,208-byte 무스필 stream이지만 같은
근사 모델에서 133.79 cycles로 열세이고, LLVM-MCA 16에는 Lion Cove/Skymont
model이 없다. 전체 100-build 결과와 shortlist 100,000-case 검증은
[`screen_255h_toolchains_02.py`](../solutions/02_optimization/screen_255h_toolchains_02.py),
[`255h_toolchain_screen_02.json`](../solutions/02_optimization/255h_toolchain_screen_02.json)에
고정했다. 현재 제출 scalar는 안전한 incumbent로 유지하고, 122-instruction
AVX2를 255H의 최우선 target-only 후보로 올렸다.

### 7차: 128-bit 분할, codegen 재탐색과 측정 안정성

YMM 네 lane을 한 번에 갱신하면 instruction 수는 작지만 vector dependency
chain이 하나다. 두 XMM 그룹으로 나누어 chain 두 개를 병렬화하면 latency를
숨길 수 있는지 네 방식으로 검사했다.

| 분할 방식 | instructions | bytes | hot memory | Alder 근사 / YMM |
|---|---:|---:|---:|---:|
| contiguous XMM 두 개 | 242 | 1,349 | 50 | 2.23x |
| reversal-orbit pair | 248 | 1,383 | 50 | 2.35x |
| 두 그룹 직렬 계산 | 250 | 1,303 | 30 | 1.78x |
| lane shuffle 재계산 | 288 | 1,509 | 30 | 1.91x |

네 후보 모두 exact GCC 13.3, 공식 vector, 임의 state/ADD/XOR 상수
100,000건의 1/20-round 검증을 통과했다. 하지만 128-bit 명령 두 개가 YMM
명령 하나를 대신하고 register pressure로 invariant가 spill되어, 가장 좋은
정적 후보도 Zen 2 근사에서 현 YMM의 1.36배 cycle이었다. 명확한 정적 열세를
공유 VM noise로 다시 선별하지 않고 host timing과 manifest 등록을 생략했다.
도구, 네 source와 결과는
[`screen_split_simd_02.py`](../solutions/02_optimization/screen_split_simd_02.py),
[`split_simd_results_02.json`](../solutions/02_optimization/split_simd_results_02.json)에
남겼다.

별도의 codegen screen은 exact GCC 13.3과 Clang 21의 target/tune,
scheduler, register allocator, loop alignment와 source 표현을 113개 build로
확장했다. 그중 100개가 exact complete-loop audit를 통과했고, 정적 Pareto
후보와 추출 가능한 모든 source rewrite 14개는 다시 100,000-case 직접 검증을
통과했다.
GCC의 `-fira-region=one`은 loop를 579에서 569 bytes로 줄였지만
122 instructions, hot memory 0, Alder/Zen 2 근사 `100.03/180.03` cycles는
같았다. Clang 기본 loop는 548 bytes였지만 같은 instructions/cycles였고 최종
compiler도 아니다.

rotate를 만드는 complementary left/right shift는 set-bit 위치가 겹치지
않아 `OR == XOR`이다. 이를 `VPOR` 대신 `VPXOR`로 바꾼 source도 두 compiler의
100,000-case 검증을 통과했다. 그러나 122 instructions와 579/548 bytes,
memory 0, 정적 cycle이 그대로였고 opcode만 `20 VPOR + 20 VPXOR`에서
`40 VPXOR`로 변했다. 모든 YMM 값을 낮은 register에 고정한 source는 563 bytes로
줄었지만, GCC가 XOR 상수를 반복 load하고 reverse 값을 다시 만들어 124
instructions/hot memory 1이 되었다. 정확성은 통과했어도 성능 audit에서 탈락했다.
inline assembly `RORX`로 기본 build에서도 즉시값
rotate를 강제한 compact pair 구현도 정확했지만 `gcc -O3`가 public wrapper
call을 남겨 timed loop가 25 bytes/8 instructions/call 1이었다. 결국 높은
inline limit가 여전히 필요해 기존 adaptive score 경로보다 낫지 않았다.
전체 matrix는
[`avx2_codegen_screen_02.json`](../solutions/02_optimization/avx2_codegen_screen_02.json)에
있다.

CPU 2의 순위 역전은 새 도구로 원인을 분리했다.
[`benchmark_timing_stability_02.py`](../solutions/02_optimization/benchmark_timing_stability_02.py)는
기존 process-isolated complete binary와 함께, scalar/AVX2 runner를 각각 4 KiB
경계에 둔 한 process의 AB/BA 측정을 수행한다. 각 sample에 wall time,
thread CPU time, serialized `RDTSCP`, CPU/`TSC_AUX`, context switch와 SMT
sibling busy fraction을 함께 기록한다.

| CPU 2 진단 | scalar/AVX2 paired median | 95% CI |
|---|---:|---:|
| process-isolated | 0.8768x | 0.859--0.891 |
| same-process, page-aligned AB/BA | 0.9225x | 0.8845--0.9290 |

각각 warm-up 6회, 3,000,000 calls, 32 samples와 100,000-case correctness/
exact audit를 사용했다. same-process의 wall/thread/TSC 비는 0.000003 이내로
일치했고 migration과 `TSC_AUX` 변화는 0이었다. 더 중요한 점은 CPU 1/2/3의
scalar 및 AVX2 exact binary와 normalized loop hash가 모두 같은데, AVX2
median은 0.78%만 변하고 scalar median은 45.89% 변했다는 것이다. 따라서
역전은 AVX2 source나 timer가 아니라 공유 VM의 scalar 처리율 변화에서
발생했다. sibling busy fraction과 scalar time의 상관이 더 컸지만 이 환경에는
APERF/MPERF, cpufreq와 performance counter가 없어 SMT contention 또는
virtualized frequency를 원인으로 확정하지 않았다. 원시는
[`timing_stability_results_02.json`](../solutions/02_optimization/timing_stability_results_02.json)이며
255H 예측에는 사용하지 않는다.

### 8차: single-scratch assembly, phase-stagger와 공식 255H 표

고정 register 실험의 563-byte 결과는 encoding 방향은 맞지만 live range가 너무
많다는 신호였다. 그래서
[`screen_avx2_inline_asm_alloc_02.py`](../solutions/02_optimization/screen_avx2_inline_asm_alloc_02.py)는
무차별 register-map 탐색 대신 scratch 1/2개, allocator 자유 배치, value만 pin,
상수/control 부분 pin 등 최초 10가지만 exact GCC 13.3으로 검사했다.

성공한 형태는 상태만 `ymm0`에 고정하고 rotate를 `scratch = value >> r`,
`value <<= l`, `value |= scratch` 순서로 쓰는 것이다. 나머지 상수와 shift-count는
GCC에 맡겼다. 그 결과
당시 single-scratch 형태는 기존과 같은 122 instructions, hot memory 0, Alder/Zen 2 근사
`100.03/180.03`을 유지하면서 loop를 579에서 **569 bytes**로 줄였다. 같은
569-byte인 `-fira-region=one`과도 normalized hash가 다른 stream이다. 제공된
기본 GCC command, 공식 vector, 임의 state와 임의 ADD/XOR 상수 100,000건의
1/20-round 검증을 모두 통과했다. 다른 8개 assembly 배치는 124 instructions와
hot load 1--2개를 남겨 탈락했다. 전체 matrix는
[`avx2_inline_asm_alloc_results_02.json`](../solutions/02_optimization/avx2_inline_asm_alloc_results_02.json)에
있다.

다른 알고리즘으로는 word-reversal orbit의 phase를 어긋나게 배치했다.
`T_j(x)=BSWAP(ROL(x,r_j) XOR k_j)+a_{3-j}`일 때 `[x0,T3(x3)]`,
`[x1,T2(x2)]`를 만들고 각 pair에 19개 immediate-rotate stage와 한 lane
epilogue를 적용한다. 임의 상수에도 정확하고 memory-free지만 두 XMM stream 때문에
257 instructions/1,253 bytes가 됐다. LLVM-MCA는 현 YMM 대비 Alder
`1.160x`, Zen 2 `0.795x`로 상반된 예측을 냈다.

이를 실제 반복 측정으로 확인했다. CPU 1과 CPU 3에서 각 후보를 6회 warm-up한 뒤
3,000,000 calls를 balanced 순서로 32 samples 측정했다. 매 campaign에서 공식
vector, 임의 state/상수 100,000건과 실제 timing binary audit를 먼저 통과시켰다.

| affinity | 569B asm speedup (current/asm), 95% CI | phase speedup (current/phase), 95% CI |
|---|---:|---:|
| CPU 1 | 0.999x (0.998--1.002) | 0.758x (0.754--0.764) |
| CPU 3 | 1.000x (0.998--1.002) | 0.756x (0.751--0.764) |

569-byte source는 두 affinity 모두 통계적 동률이고, phase 후보는 유리했던 Zen 2
정적 예측과 반대로 처리량이 약 24% 낮고 같은 작업의 실행 시간은 약 32%
길었다. 따라서 전자는 255H target-only 후보로만
추가하고 후자는 탐색 source만 보존한다. raw 결과는
[`eighth_wave_timing_02_cpu1.json`](../solutions/02_optimization/eighth_wave_timing_02_cpu1.json),
[`eighth_wave_timing_02_cpu3.json`](../solutions/02_optimization/eighth_wave_timing_02_cpu3.json),
정적·대수 기록은
[`phase_staggered_results_02.json`](../solutions/02_optimization/phase_staggered_results_02.json)에
있다.
처음에는 benchmark가 source를 temporary directory로 복사하면서 phase 파일의
상대 include 기준을 잃어 timing 전에 compile이 중단됐다. 측정 driver가 원래
source directory를 `-iquote`로 candidate object와 performance build 모두에
전달하고 당시 schema 4에도 기록하도록 고친 뒤 두 campaign을 처음부터 다시 실행했다.

추가 GCC AVX backend flag도 63개 새 조합과 기준 2개를 검사했다. preferred
vector width, unaligned load/store split, VEX/vzeroupper, move/store width,
cost model, partial/AVX tune을 포함했고 65/65 exact loop의 normalized stream은
기존 generic/Alder 두 종류로 수렴했다. 그러나 `(stream hash, loop-start mod 64)`로
구분하면 generic offset `0/8/24/40/48`과 Alder offset `8/16/48`, 총 **8개 배치
클래스**다. 각 클래스 대표 8개가 임의 100,000건을 통과했다. instruction count와
proxy cycle은 같아도 frontend 배치는 LLVM-MCA가 보지 못하고 기존 AMD 정렬
sweep에도 유의한 승자가 없었으므로 nonbaseline 대표 7개를 255H target-only
manifest 후보로 남겼다. 즉
[`gcc133_avx_flags_results_02.json`](../solutions/02_optimization/gcc133_avx_flags_results_02.json)은
컴파일러 flag 공간의 재현 가능한 음성 결과다.

실제 target을 더 잘 이해하려고
[`analyze_255h_instruction_model_02.py`](../solutions/02_optimization/analyze_255h_instruction_model_02.py)는
Intel ARK topology와 Arrow Lake PerfMon/255H ECI의 core 설명, Intel 공식
Skymont/Crestmont instruction package의 선택 행을 hash로 검증한다. Skymont
download는 Xeon 6 E-core용이라는 이름이므로 client 255H E-core로 수치를 옮기는
것은 조건부다. 또한 Arrow Lake PerfMon은 LP-E를 Crestmont로 부르지만 Intel의
255H 전용 ECI 문서는 두 LP-E를 "additional Skymont cores"라고 설명한다.
따라서 Crestmont 표는 PerfMon mapping이 맞을 때의 민감도 분석으로만 사용한다.
AVX2 hot 여섯 연산은 두 표에서 latency가 모두 1이라
`parallel shifts 1 + OR/XOR/SHUF/ADD 4`의 20-round critical path는 100
cycles다. scalar 80-cycle 비교는 정확한 `RORX r64`와 여섯 `LEA` 행이 없어
r32 RORX/ADD를 대신 쓴 민감도 분석일 뿐이다. 2026-07-23에 고정한 Intel
catalog에서는 Lion Cove 공식 per-instruction 표도 확인하지 못했고, isolated throughput은 port 공유·frontend·주파수·whole-loop
효과를 담지 않는다. 따라서
[`instruction_model_255h_02.json`](../solutions/02_optimization/instruction_model_255h_02.json)은
gap을 명시하고 승자를 선택하지 않는다.

마지막 성능 순위는 255H에서만 결정할 수 있으므로
[`autotune_02_255h.py`](../solutions/02_optimization/autotune_02_255h.py)를
추가했다. 이 도구는 `probe -> screen -> confirm -> decide`를 분리하고, logical
CPU별 pinned CPUID와 Linux topology를 기록한다. P/E는 CPUID로 나누되 LP-E는
둘 이상의 보조 신호가 동의할 때만 분류한다. 두 session, core type마다 서로
다른 physical representative 두 개, compiler/source/manifest hash와 schema 5
정확성·실측 binary SHA-256/assembly gate가 모두 있어야 한다. session 이름만
바꾸고 같은 artifact path나 content hash를 재사용하면 즉시 provisional이다.
각 run의 128-bit nonce를 index와 benchmark JSON 양쪽에 묶고, canonical evidence와
paired-sample hash도 비교하므로 공백이나 파일명만 바꾼 복사본도 두 번째 session이
될 수 없다.
측정 driver, loop audit, 독립 oracle/verifier, 공식 입력 ZIP, Python 실행 파일도
실제 `objdump`/`size` binary와 함께 canonical SHA-256 protocol fingerprint로
고정한다. `screen` 이후 이 중 하나가
바뀌거나 두 confirmation의 fingerprint가 다르면 재측정을 요구하며, 오래된
protocol로 만든 topology probe도 새 `screen`에서 거부한다. 정확성
레코드 역시 무작위 상태와 무작위 ADD/XOR 상수의 1/20-round 검사를 명시해야
하며 runner가 실제 출력 count/seed/round/constant/PASS를 정확히 파싱한다.
reference TU는 후보 flag와 분리하고, candidate source는 한 번만 snapshot하여
원본 및 benchmark-iteration rewrite hash를 모두 기록한다. 따라서 단순히 PASS
문자열이나 검증 전용 flag를 끼워 넣어 판정을 통과할 수 없다.
topology는 cache 배열 내부 원소까지 object인지 검사해 malformed nested
입력을 traceback 없이 fail-closed한다. 초기 8-case 통합 smoke는
`portable_rol` diagnostic의 manifest에
`portable-inline-320`용 `-finline-limit=2000`이 빠진 것도 발견했다. flag를
명시한 뒤 예상한 1,060-byte/323-instruction loop와 8개 audit가 모두 통과했다.
5차 후보를 포함한 균형 순서 15-case screen에서도 15개 직접 검증과
15개 exact-binary audit가 모두 통과했다. 작은 AMD/GCC12 confirm 두 번을
`decide`에 연결한 회귀에서는 255H/GCC13.3, sample, warm-up, iteration,
random-case 조건을 각각 누락 사유로 제시하고 incumbent를 유지했다.
부분 언롤과 AVX2를 추가한 19-case smoke는 직접 검증/audit 19/19를 통과했다.
서로 다른 569-byte stream인 `-fira-region=one`과 당시 single-scratch source를
더한 21-case smoke도 21/21을 통과했다. nonbaseline stream/alignment 대표
7개를 더해 28 case가 됐고, 현재 549-byte commutative source는 기존
single-scratch entry를 대체한다. 548-byte `DEC` 대조군과 기존 compact block2를
추가한 9차 상태는 30 case였다. 10차 counted block-2/3/5 세 후보까지 더한 최신
**33-case** manifest는 source·flag·assembly contract를 고정하고, runner가 실행
JSON에 각 source-local `-iquote` context를 기록한다. 짧은 provisional-host
timing 자체는 성능 결론에 쓰지 않는다.
P-core 모든 campaign에서
paired median `>= 1.010`, 보정 lower bound `> 1.005`를 만족하지 못하거나 복수 후보가
동시에 통과하면 incumbent를 유지한다.

### 9차: 반복 의미 검증, 549-byte encoding과 compact block

9차에서는 먼저 성능보다 측정의 의미를 보강했다. 기존 runner는 후보의 공개
1/20-round 함수를 별도 verifier에서 확인하고 실제 timing loop의 assembly도
감사했지만, timing용 `main`이 선언된 횟수만큼 상태를 연속 갱신했는지는 확인하지
않았다. 회귀용으로 timing loop만 `iterations/2`회 실행하는 source를 만들면 공개
함수 검증과 322-instruction/80-core-operation audit를 모두 통과하면서 약
**2.253x**의 거짓 가속으로 보였다.

schema 5는 이 공백을 다음과 같이 닫는다.

1. 독립 reference가 고정 초기 상태에 20-round 함수를 정확히 `iterations`회
   적용해 최종 256-bit 상태를 계산한다.
2. 모든 후보의 semantic preflight, warm-up, measured process가 선언한 반복 수와
   그 최종 상태를 정확히 출력해야 한다.
3. 한 campaign의 oracle/case 집합, process 수와 canonical stdout SHA-256을
   fail-closed JSON contract로 저장하고 autotuner와 모든 consumer가 다시 검사한다.

3,000,000회·warm-up 6회·32 samples에서는 후보마다 preflight 1회까지 합쳐
**39개 process**의 최종 상태를 검증했다. 음수/0 반복, 중복·누락 출력,
oracle hash 변조와 위 절반-loop source를 고정 regression test로 남겼다. 과거
schema 2--4 JSON은 당시 성능·assembly의 역사 자료로는 유효하지만 이 반복 의미
보증을 포함한다고 해석하지 않는다.

다음 micro 최적화는 교환법칙을 encoding에 이용했다. AT&T 3-operand 표기에서
`VPOR`, `VPXOR`, `VPADDQ`의 두 source 순서를 바꾸어 낮은 번호의 변화 상태를
ModRM source에 두고, 높은 scratch/상수를 VEX `vvvv` 쪽으로 옮겼다. 연산과
dependency graph는 그대로지만 20개 `VPOR`가 각각 1 byte 줄어
[`contest_simd_avx2_inline_asm.c`](../solutions/02_optimization/contest_simd_avx2_inline_asm.c)는
exact GCC 13.3에서 **122 instructions/549 bytes/hot memory 0**이 됐다.

현재 여섯-instruction transform은 shift 두 개 5+5B, OR/XOR/add/shuffle
4+4+4+5B로 27B다. 따라서 현재 `sub` counter의 loop 하한은
`20*27 + 3 + 6 = 549B`다. `-mtune-ctrl=use_incdec`는 바깥 counter만 `dec`로
바꾸어 548B가 되므로 source 기본값이 아니라 target-only 대조군이다.
[`screen_avx2_commutative_layout_02.py`](../solutions/02_optimization/screen_avx2_commutative_layout_02.py)는
digest 고정 GCC 13.3에서 flag/link 34개를 검사했다. 34/34가 공식 vector와 임의
state/상수 100,000건, exact audit를 통과했고 normalized stream 5종,
stream/alignment class 9종으로 수렴했다. 모두 Alder/Zen 2 MCA
`100.03/180.03`으로 같았다. 원시는
[`avx2_commutative_layout_results_02.json`](../solutions/02_optimization/avx2_commutative_layout_results_02.json)에
있다.

알고리즘 쪽에서는 완전 언롤과 작은 loop 사이를 다시 나눴다. 두 pair를 loop body에
놓고 5회 반복하는
[`contest_simd_avx2_pair_block2.c`](../solutions/02_optimization/contest_simd_avx2_pair_block2.c)는
정적 timing region을 **136B/30 instructions**로 줄인다. 한 20-round 호출의
padding 제외 modeled 명령은 122에서 133으로 11개 늘고 실제 binary의
alignment NOP까지 포함하면 134개지만, hot memory는 0이고 MCA critical path는
여전히 `100.03/180.03`이다. block1은 75B/18 static, padding 제외 143(NOP
포함 144)이고 block5는 더 큰 321B/69 static인 대신 padding 제외 동적 수가
131(NOP 포함 132)로
2개 줄고 Alder proxy throughput도 22.2에서 21.8 cycles로 소폭 낮은 다른
절충점이었다. 이 근소한 모델 이득은 185B/39 static-instruction 증가를 target
전에 정당화하지 못했다.
scalar stage-major SSA도 만들고 첫/둘째 stage의 chain 순서 `24*24=576`개를
전수했으나 tuned scalar 기준 120.06 cycles보다 엄격히 낮은 경우는 0개였다.
재현은
[`screen_avx2_pair_blocks_02.py`](../solutions/02_optimization/screen_avx2_pair_blocks_02.py)와
[`avx2_pair_block_results_02.json`](../solutions/02_optimization/avx2_pair_block_results_02.json)에
고정했다.

마지막으로 old 569B `-fira-region=one`을 기준으로 9차 후보 네 개와
기존 current579 대조군을 CPU 1/3에서
각 3,000,000회, warm-up 6회 뒤 32 samples로 다시 측정했다.

| 후보 (old569/candidate) | CPU 1 paired median, 95% CI | CPU 3 paired median, 95% CI |
|---|---:|---:|
| 549B commutative | 1.000451x (0.999294--1.001894) | 1.000466x (0.998164--1.002395) |
| 548B incdec | 0.999555x (0.997869--1.000627) | 1.001880x (0.997620--1.004207) |
| 549B align32 | 0.998679x (0.994845--1.002219) | 1.000329x (0.995564--1.003437) |
| block2 | 0.999263x (0.997061--1.001998) | 0.999278x (0.997635--1.002321) |

모든 새 후보의 CI가 1을 포함한다. 즉 code footprint는 확실히 줄었지만 이 AMD
host에서 처리량 개선은 검출되지 않았다. raw schema-5 기록은
[`ninth_wave_timing_02_cpu1.json`](../solutions/02_optimization/ninth_wave_timing_02_cpu1.json)과
[`ninth_wave_timing_02_cpu3.json`](../solutions/02_optimization/ninth_wave_timing_02_cpu3.json)에
있다. 두 파일은 repeated-call gate를 포함하지만 10차 measurement-protocol hash
변경 전 만들어진 역사적 schema-5 증거다. 새 target confirmation에는 current
protocol로 다시 측정해야 한다. 549B, 548B와 block2는 실제 255H의 P/E/LP-E에서만
승격할 후보이고 scalar submission incumbent는 그대로다.

### 10차: counted frontend, codegen 경계와 측정 계약 보강

10차 알고리즘 탐색은 열 round-pair를 작은 body와 나머지 tail로 다시 나눴다.
[`screen_tenth_avx2_counted_frontends_02.py`](../solutions/02_optimization/screen_tenth_avx2_counted_frontends_02.py)는
conventional `DEC/JNE` block 크기 1--10과 signed rel8에 들어가는 x86 `LOOP`
대조군을 생성했다. 모든 full case가 exact GCC 13.3 complete-loop audit, 공식
vector, 임의 state·ADD/XOR 상수 100,000건의 1/20-round differential을
통과했다.

| 후보 | 정적 timing loop | 한 20-round 호출의 padding 제외 modeled 명령 |
|---|---:|---:|
| counted block 2 (`2*5`) | **122B / 29 instructions** | 133 |
| block 3 + tail 1 (`3+3+3+1`) | **238B / 53 instructions** | 129 |
| counted block 5 (`5+5`) | **292B / 65 instructions** | 127 |

세 후보 모두 hot memory가 없고 549B full-unroll과 같은
`100.03/180.03` Alder/Zen-2 dependency-path proxy를 유지한다. counted block 2는
9차 136B/30-static 구현을 엄격히 줄였다. block 3은 당시 321B/69-static block
5보다 작고 동적 명령도 `131 -> 129`로 줄이며, 새 block 5는 54B를 더 쓰는 대신
block 3보다 동적 제어 두 명령이 적다. block 4는 같은 127-dynamic인 block 5보다
크고, block 6--10은 transform을 전부 펼친 뒤 제어만 더해 full549에 지배된다.
x86 `LOOP`는 byte 수가 작아도 Intel proxy에서 µop/throughput이 나빠져 정적
근거만으로 승격하지 않았다. 전체 Pareto/음성 결과와 exact CFG trace는
[`tenth_avx2_counted_frontends_results_02.json`](../solutions/02_optimization/tenth_avx2_counted_frontends_results_02.json)에
있다.

codegen 축은 VEX register 위치와 정확한 식 재결합을 더 좁혔다. high state
register가 VEX.vvvv/destination에 있고 scratch와 상수가 low ModRM r/m이면
`ymm8/12/15`도 모두 549B/122 instructions로 baseline과 동률이다. high state를
잘못 ModRM에 두면 609B, scratch까지 high register가 되면 569B로 늘었다.
`VPADDQ` rotate merge도 instruction/byte/model tie였다. 상수 XOR을 right-shift
branch로 옮긴 표현은 Intel proxy 두 개가 `100.03`으로 그대로이고 Zen-2
교차-architecture proxy만 `180.03 -> 160.03`이어서 target 진단으로만 남겼다.
source-controlled offset 14개도 normalized stream은 같아 주소 없는 LLVM-MCA로
frontend 경계를 판정하지 않았다. 재현은
[`screen_tenth_codegen_02.py`](../solutions/02_optimization/screen_tenth_codegen_02.py)와
[`tenth_codegen_results_02.json`](../solutions/02_optimization/tenth_codegen_results_02.json)에
고정했다.

scalar의 same-register rotate도 별도 대조했다. 강제 `ROL`은
**322 instructions/1,052B**로 `RORX` incumbent 1,211B보다 159B 작지만,
Alder/Meteor proxy가 `121.06 cycles/402 µops -> 138.13/482`로 악화됐다.
same-register `SHLD`는 rotate 의미는 정확해도 dependency microprobe가 Intel
proxy에서 명령당 `3.03` cycles라 `RORX`의 `1.03`보다 길어 full expansion 전에
기각했다. 이는 Intel SDM의 instruction 의미·encoding과 llvm-mca의 정적 모델을
사용한 선별 결과일 뿐 255H 측정이 아니다. 자세한 audit은
[`tenth_codegen_scalar_rotate_results_02.json`](../solutions/02_optimization/tenth_codegen_scalar_rotate_results_02.json)에
있다.

측정 도구에는 repeated final state를 우회하는 세 실제 회귀를 추가했다.

1. 짧게 잰 뒤 `clock()` 밖에서 빠진 계산을 끝내는 후보는 final state가 맞아도
   child process CPU 시간에 비해 timed region이 짧다. 1,000,000회 이상에서는
   `inner/child CPU` median `[0.65,1.05]`를 요구해 거절한다.
2. 주 반복 수의 알려진 최종 상태를 timer 뒤에 상수로 쓰는 후보에는 fresh
   128-bit nonce, campaign/source hash와 주 반복 수에서 `4096..65535`의 별도
   iteration을 유도해 독립 oracle와 비교한다.
3. 출력 average만 절반으로 쓰는 후보에는 total/average/iteration의 반올림
   구간 일치를 요구하고, 실제 ns를 average가 아니라 `total/iterations`에서
   계산한다.

autotuner도 raw sample 수, total/average/child-CPU 배열, alternate challenge의
nonce digest·campaign/source binding과 coverage eligibility를 다시 검증한다.
POSIX child CPU accounting이 없으면 fail-closed하고 백만 회 미만은
diagnostic-only다. 이 방어선은 재현한 세 우회를 막지만 runner를 알고 작성한
모든 악성 C의 부재를 암호학적으로 증명하지는 않는다.

새 counted block 2/3/5를 full549와 CPU 1/3에서 각각 3,000,000회, warm-up 6회,
balanced sample 32개로 current schema 5 재측정했다.

| 후보 (`full549/candidate`) | CPU 1 paired median, 95% CI | CPU 3 paired median, 95% CI |
|---|---:|---:|
| scalar incumbent | 1.061x (1.041--1.120) | 1.032x (1.021--1.057) |
| 기존 intrinsic block 2 | 1.005x (0.996--1.013) | 1.000x (0.999--1.001) |
| counted block 2 | 1.003x (0.994--1.009) | 0.999x (0.997--1.003) |
| block 3 + tail 1 | 1.005x (1.001--1.014) | 1.001x (0.997--1.004) |

CPU 1은 실행 중 host 부하 변화로 median이 크게 이동한 nonstationary
campaign이었다. 그 안의 block-3 약 0.5% 신호는 CPU 3에서 재현되지 않았고
autotuner의 1% 승격 기준에도 못 미친다. 따라서 정적 Pareto 후보 세 개를 255H
target-only manifest에 보존하되 full549나 scalar incumbent를 교체하지 않는다.
raw는
[`tenth_wave_timing_02_cpu1.json`](../solutions/02_optimization/tenth_wave_timing_02_cpu1.json)과

있다. 실제 Core Ultra 7 255H는 아직 측정하지 못했다.

### 11차: 정상성 gate와 범위 제한 ISA 합성

10차 CPU 1처럼 campaign 도중 성능 단계가 이동한 자료를 자동으로 승격에서
제외하도록 schema 5에 four-fixed-block stationarity record를 추가했다.
chronological sample을 사전에 정한 네 block으로 나누고 최소 16 samples를
요구한다. `N`-case screen은 `4*N`의 배수, 2-case confirmation은 최소 40이면서
8의 배수여야 각 block의 case position이 균형을 이룬다. case의 block-median
최대/최소 spread가 5%를 넘거나 incumbent/candidate paired-effect spread가 2%를
넘으면 diagnostic-only다. block별 ratio가 `0.995` 미만과 `1.005` 초과 양쪽에
있으면 0.5%보다 큰 material sign reversal도 기록한다.

autotuner는 raw sample에서 이 record를 독립 재계산하므로 요약 field·threshold·
raw binding이 다르면 fail-closed한다. screen에서는 불안정한 해당 candidate
pair만 제외하고 confirmation/`decide`에서도 실제 pair만 판정한다. schema 숫자는
5를 유지하지만 field와 canonical protocol hash가 바뀌었으므로 그 전의 모든
schema-5 timing JSON은 역사 자료다. 이 고정 effect-size gate는
[Barrett et al.](https://arxiv.org/abs/1602.00602)의 steady-state/changepoint
문제와
[Kalibera/Jones](https://doi.org/10.1145/2464157.2464160)의 반복 계층·effect-size
설계를 참고했지만 PELT나 전체 hierarchical model을 재현한 것은 아니다.

현 protocol의 AMD/GCC12 재측정은 3,000,000 calls, warm-up 6, balanced
samples 24, random differential 100,000건을 사용했다.

| affinity | 정상성 | 결과 |
|---:|---|---|
| CPU 1 | full549 absolute spread `2.3157%`; AVX 네 pair eligible; scalar만 `9.0577%`로 diagnostic-only | AVX paired median `0.999624--1.002591x`, 모든 95% CI가 1 포함, 1% 승격 미달 |
| CPU 3 | full549 absolute spread `8.2770%`; AVX pair-effect spread 최소 `2.2451%`, 대부분 sign reversal | campaign 전체 diagnostic-only, 승격 불가 |

raw는
[`stationarity_gate_timing_02_cpu1.json`](../solutions/02_optimization/stationarity_gate_timing_02_cpu1.json)과
[`stationarity_gate_timing_02_cpu3.json`](../solutions/02_optimization/stationarity_gate_timing_02_cpu3.json)에
있다. 새 gate로도 scalar incumbent는 바뀌지 않는다.

알고리즘 쪽 마지막 축은
[`screen_eleventh_isa_synthesis_02.py`](../solutions/02_optimization/screen_eleventh_isa_synthesis_02.py)로
`BSWAP64` 뒤 non-byte rotate를 세 명령으로 합성하는 탐색이었다. qword logical
shift, word-local arbitrary fixed byte shuffle, XOR/OR 또는 disjoint field의
carry-free ADD grammar에서 one-instruction와 parallel `two unary + combine`은
전수했고, 나머지 세 연산 DAG topology는 bit-loss/bijectivity/projection 구조
논증으로 제외했다. 네 rotation 모두 **그 범위 안에서만 UNSAT**다. 모든 x86
opcode나 더 긴 network의 전역 최적성 증명은 아니다.

정확한 split-shuffle 대조군 세 개는 공식 vector, complete-loop audit, 임의
state·ADD/XOR 상수 100,000건의 1/20-round를 모두 통과했지만, round마다
`VPSHUFB`가 하나 늘어 `122 instructions/549B`를 `142 instructions/669B`,
`142/669B`, `142/689B`로 키웠다. shuffle은 상수 변환과 함께 XOR을 통과할 수
있지만 modular ADD carry 때문에 round 경계 shuffle을 상쇄할 수 없다.
[`eleventh_isa_synthesis_results_02.json`](../solutions/02_optimization/eleventh_isa_synthesis_results_02.json)에
scope, UNSAT check와 counterexample를 고정했으며 새 후보는 없다.

LLVM 19.1.7의 `arrowlake` 이름은
[`X86.td`](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.7/llvm/lib/Target/X86/X86.td)에서
`AlderlakePModel`에 매핑된다. 테스트한 여섯 LLVM 19 label도 각 stream에서
동일한 cycles/instructions/µops/RThroughput을 냈다. 따라서 이는
[llvm-mca](https://llvm.org/docs/CommandGuide/llvm-mca.html)의 정적 proxy일 뿐
255H P/E/LP-E 모델 근거가 아니다.

## 결론

복원한 구조와 rotation은 모든 제공·random vector를 통과한다. 첫 최적화는
전체 byte reversal을 word reversal+`BSWAP64`로 축약한 것이고, 이번
최적화는 두 라운드 뒤 word 위치가 복원된다는 대수적 성질로 네 독립
chain을 만든 것이다. 10개 pair의 완전 전개와 BMI2 scalar는 안전한 incumbent이고,
같은 source의 cross-call inlining이 두 affinity에서 `1.116x/1.118x`를 개선했다.
이번에 네 chain을 YMM lane에 직접 놓은 122-instruction AVX2 후보도 찾아 AMD의
두 physical affinity에서 scalar 대비 `1.275x/1.248x`를 얻었지만, 다른
affinity에서는 `0.940x`로 순위가 뒤집혔다.
동일 binary의 후속 진단은 AVX2 median 범위가 0.78%인 동안 scalar가 45.89%
변했음을 확인했고, 두 XMM 분할과 113-build codegen 재탐색도 source-level
승자를 만들지 못했다. 8차의 single-scratch assembly는 exact loop를 10 bytes
줄였지만 두 32-sample AMD campaign에서 `0.999x/1.000x` 동률이었고,
phase-stagger도 `0.758x/0.756x`로 기각했다. 9차에서는 교환 피연산자의
VEX operand 위치를 바꿔 동일한 122 instructions/0 hot memory를 **549B**로
줄였고, 두 pair씩 반복하는 block2는 정적 region을 **136B/30
instructions**로 줄였다. 그러나 schema-5 32-sample 재측정의 모든 새
후보도 두 affinity에서 CI가 1을 포함했다. 따라서 AMD VM의 역전이나
정적 byte 감소만을 선택 근거로 사용하지 않는다. 10차 counted frontend는
block-2/3/5를 각각 **122B/29-static/133-dynamic**,
**238B/53/129**, **292B/65/127**로 더 줄였다. CPU 1 block-3의 약 0.5%
신호는 nonstationary였고 CPU 3에서 재현되지 않았으며 승격 기준 미달이었다.
high-register VEX 배치와 `VPADDQ` merge는 동률,
right-branch XOR은 Zen proxy만 개선됐고, 작은 강제 `ROL`은 Intel proxy
uop/cycle이 늘어 승격하지 않았다.
11차의 fixed-block gate는 새 CPU 1 AVX pair를 모두 안정으로 판정했지만 모든
CI가 1을 포함하고 최대 paired median도 `1.002591x`였으며, CPU 3은 full549
absolute drift `8.2770%`에서 탈락했다. 세 명령 AVX2 합성도 명시한 grammar
안에서 UNSAT였고 exact split-shuffle은 142 instructions/669--689B로 커졌다.
그러나 최종 권장은 실제 255H 확인 전까지 기본 build 호환성을 유지한 adaptive
scalar source와 `-mbmi2 -finline-limit=2000` score build다. GCC 13.3에서도 call
제거와 limit 700/2000의 완전 동일성을 확인했다. 문서화한 algorithmic/ISA,
codegen, cache/frontend와 micro 범위는 새 승격 후보 없이 닫혔으므로, 남은
것은 실제 255H에서 AVX2와
generic/Alder/Alder+IRA, source order `2,1,0,3` 및 두 backend scheduler
stream, old 569-byte AVX2 stream, 기준 외 7개 배치 대표,
549/548-byte encoding과 기존/new compact block 계열을 포함한 **33-case**
manifest의 순위를 보수적으로 판정하는 일이다. current schema 5는 공개 함수
검증과 assembly audit, 모든 process의 반복 최종 상태뿐 아니라 total-derived
timing, child-CPU coverage, nonce-derived alternate iteration과 raw-recomputed
stationarity도 검증한다. 실제 절차는 `probe -> screen ->` 서로 다른 시간대의
`confirm` 두 번 `-> decide`다. 이는
재현한 우회에 대한 방어선이며 임의의 악성 C를 증명한다고 과장하지 않는다.
raw sample, exact-binary audit와 실패 전략까지
남겼고 자동 판정 도구도 불완전한 topology나 복수 승자에서는 incumbent를
유지한다.
