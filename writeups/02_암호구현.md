# 2. 암호구현 - 256비트 permutation 복원과 성능 최적화

## 문제와 제출 목표

상태는 네 개의 64비트 word이고 한 라운드는 다음 네 종류의 연산을 한
번씩 사용한다.

- word별 rotate-left
- 네 word와 상수의 XOR
- 32바이트 permutation
- word별 modulo `2^64` 덧셈

1라운드의 순서와 서로 다른 rotation 네 개를 복원하고, 같은 함수를
20라운드 반복해야 한다. 정확성 30점과 문서 30점은 절대평가지만 성능
40점은 상대평가이므로, 정답을 찾은 뒤 실제 제출 harness의 한 상태
직렬 workload를 최적화해야 한다.

최종 결과는 다음과 같다.

```text
round = rotate -> XOR -> reverse all 32 bytes -> add
rot   = {43, 7, 29, 14}
```

## 1. 구조와 rotation 복원

각 단계는 역연산이 있다.

- 덧셈은 같은 상수를 빼면 된다.
- `shuffle_map[i]=31-i`인 32바이트 reversal은 자기 자신의 역이다.
- XOR은 같은 상수를 다시 XOR하면 된다.
- rotate 값은 허용 범위 `1..63`을 모두 검사할 수 있다.

출력 `out`에 역연산을 적용한다.

```text
t0 = out - constants1              (word별 mod 2^64)
t1 = reverse_all_32_bytes(t0)
t2 = t1 XOR constants2
```

각 word `i`에서 `ROTL64(input[i],r_i)==t2[i]`인 `r_i`를 찾는다.
`solutions/solve_02_permutation.py`는 첫 벡터 하나에 의존하지 않고 제공된
1,000개 벡터에서 후보 집합을 모두 교차한다. 각 word에 정확히 하나씩
`43,7,29,14`가 남고, forward evaluation이 모든 벡터와 일치한다.

## 2. 기준 구현과 1차 특수화

기준 구현은 제공된 네 함수를 복원한 순서로 호출한다.

```c
rotate_words_left_64wise(state, rot);
xor_constants_256wise(state, constants2);
shuffle_bytes_256(state, shuffle_map);
add_constants_64wise(state, constants1);
```

하지만 고정 map은 임의 permutation이 아니라 전체 byte reversal이다.

```text
reverse32(x0,x1,x2,x3)
 = (BSWAP64(x3), BSWAP64(x2), BSWAP64(x1), BSWAP64(x0))
```

따라서 32회의 indexed byte copy와 임시 배열 두 개를 네 번의
`BSWAP64`로 바꿀 수 있다. 한 라운드는 다음 네 식이 된다.

```text
y0 = BSWAP64(ROTL64(x3,14) XOR C2[3]) + C1[0]
y1 = BSWAP64(ROTL64(x2,29) XOR C2[2]) + C1[1]
y2 = BSWAP64(ROTL64(x1, 7) XOR C2[1]) + C1[2]
y3 = BSWAP64(ROTL64(x0,43) XOR C2[0]) + C1[3]
```

고정 rotation은 즉시값 instruction이 되고, GCC/Clang에서는
`__builtin_bswap64`가 target byte-swap instruction으로 내려간다. 이
register-loop 버전이 이전 제출이었다.

## 3. 두 라운드 합성과 최종 구현

한 라운드는 word 순서를 뒤집는다. 두 라운드를 묶으면 이 reversal이
상쇄되어 각 출력 word가 같은 위치의 원래 word에만 의존한다. source
word `j`에 rotate, XOR, byte-swap, destination add를 적용하는 함수를
`T_j`라 쓰면 두 라운드는 다음 네 독립 chain이다.

```text
x0 <- T3(T0(x0))
x1 <- T2(T1(x1))
x2 <- T1(T2(x2))
x3 <- T0(T3(x3))
```

이 식은 round마다 `x0..x3`를 서로 교환하는 형태보다 compiler가 네
독립 dependency chain을 보기 쉽다. 최종 helper는 이 2-round block을
10번 완전히 전개해 loop branch를 없앤다.

평가 CPU가 고정되어 있으므로 helper에 GCC `target("bmi2")`를 국소
지정했다. GCC가 constant rotate를 non-destructive `RORX`로 선택할 수
있고, 이 instruction은 condition flag도 변경하지 않는다. 전체 파일은
문제에서 제공한 기본 명령 그대로 컴파일된다.

문제의 수정 범위에는 외부 helper 추가가 허용된다. 제공된 20-round
`for`문의 허용된 line에서 helper가 20라운드를 한 번에 수행하고 `r=19`로
남은 중복 iteration을 끝낸다. 함수는 임의 상태에 같은 permutation을
적용하며 benchmark input이나 정답 상태를 하드코딩하지 않는다.

## 4. 여러 최적화 후보 비교

`solutions/02_optimization/benchmark_02_candidates.c`에는 같은 reference를
공유하는 후보 여덟 개가 있다. 각 후보는 별도 binary로 컴파일해 큰
unrolled function끼리 instruction-cache layout에 영향을 주지 않게 했다.
모든 후보가 제공 벡터와 100,000개 random differential case를 통과한 뒤
warm-up과 반복 측정을 수행한다.

AMD EPYC 7B12, GCC 12.2.0, `-O3 -march=native`, CPU 2 고정,
2,000,000-call 표본 15개의 후보 선별 결과는 다음과 같다.

| 후보 | 중앙값 ns/20-round | MAD ns | 현 제출 대비 |
|---|---:|---:|---:|
| 이전 submission 형태 | 41.894 | 2.834 | 1.000x |
| register loop | 40.655 | 3.083 | 1.031x |
| paired AVX2 loop | 39.718 | 0.131 | 1.055x |
| paired scalar full-unroll | 36.824 | 2.617 | 1.138x |
| paired scalar full-unroll + BMI2 | **36.249** | 3.195 | **1.156x** |
| one-state AVX2 | 73.630 | 0.266 | 0.569x |

이 표는 후보 선별용 steady microbenchmark다. 실제 제출에서 compiler가
무엇을 inline하는지가 다르므로 이것만으로 최종안을 정하지 않았다.

### 성능이 나빠진/채택하지 않은 후보

한 상태를 AVX2 register 하나에 넣는 방법은 네 lane rotate를 위해
variable left/right shift와 OR가 필요하고, 이어 XOR, byte shuffle,
128-bit-half permutation, add가 하나의 긴 직렬 chain을 이룬다. 네 scalar
word의 짧은 chain 네 개보다 느려 73.630ns가 나왔으므로 제외했다.

네 상태를 lane별로 transpose한 batch-4 AVX2는 throughput은 좋아졌지만
공식 API와 timing loop가 상태 하나를 직렬 갱신하므로 제출에 쓸 수 없다.
이는 다른 workload에는 유효한 최적화지만 이 문제의 score metric과
다르다.

compiler가 두 라운드 식을 AVX2로 SLP vectorize한 paired loop는 표본이
매우 안정적이었지만 이 AMD host에서는 BMI2 scalar보다 느렸다. target
Intel에서는 execution-port와 latency balance가 다를 수 있다는 이유로 처음에는
재측정 후보로 남겼다. 그러나 뒤의 18-candidate 심층 검토에서 loop와 unroll이
각각 0.9566x, 0.9076x에 그쳐 최종 A/B 목록에서는 제외했다.

BMI2 없는 inline scalar full-unroll도 제출형 별도 후보로 측정해
34.748ns를 얻었고 BMI2의 34.669ns와 거의 같았다. 현재 제출은 local
winner인 BMI2를 선택했지만, 작은 차이는 target 재측정 대상이다.

## 6. 제출 형태 반복 benchmark

기존 benchmark는 `optimized_20_rounds`를 매 outer iteration마다
`NOINLINE` 호출했지만, 이전 실제 `contest.c`는 GCC가 helper와 20-round를
`main`의 timing loop 안으로 inline했다. 이 차이는 수 ns급 후보를
판정할 때 무시할 수 없다. 또한 `median(before)/median(after)`와 각
round의 speedup 중앙값은 실제 측정에서 약 4% 달라진 적이 있다.

새 `solutions/benchmark_02_permutation.py`는 score-facing 검사를 다음처럼
수행한다.

- 최적화 전 `contest.c`를 `contest_before.c`로 보존하고 최종 제출과
  각각 별도 complete binary로 컴파일한다.
- compiler 구조를 유지한 채 timing-loop iteration만 길게 바꾼다.
- 3개 warm-up process를 버리고 기본 21개 표본을 측정한다.
- 한 logical CPU에 고정하고 case 순서를 cyclic rotation/reversal한다.
- 매 표본에서 공식 1,000/20-round vector를 검사한다.
- raw internal `clock()`와 외부 wall time, median, MAD, p05/p95, bootstrap
  median 95% interval, paired speedup을 JSON으로 남긴다.
- outlier를 지우지 않고 3-MAD flag만 표시한다.

10,000,000-call, warm-up 3회, measured 15회 캠페인 결과:

| 제출형 구현 | 중앙값 | MAD | p05--p95 |
|---|---:|---:|---:|
| 이전 scalar | 36.799 ns | 0.924 ns | 35.766--45.773 ns |
| 2-round unroll + BMI2 | 34.669 ns | 2.232 ns | 32.384--46.657 ns |

같은 measurement round끼리 계산한 speedup 중앙값은 **1.068x**, MAD는
0.045x, bootstrap 95% interval은 1.008x--1.105x였다. 그러나 shared VM의
다른 20,000,000-call 캠페인은 1.019x와 0.991x--1.082x interval을 냈다.
즉 local evidence는 대체로 개선 방향이지만 몇 % 차이를 이 VM만으로
확정하면 안 된다. 이후 심층 검토까지 반영한 마지막 선택 절차는 최종
Intel Core Ultra 7 255H/GCC 13.3.0에서 BMI2 full-unroll과 작은 unroll5를
같은 raw-sample protocol로 비교하는 것이다.

재현 명령:

```bash

  --cpu 2 --iterations 10000000 \
  --warmups 3 --samples 15 --random-cases 100000 \
  --json /tmp/challenge02-benchmark.json
```


## 7. 알고리즘과 cache/micro 최적화 심층 재검토

초기 후보 선별 뒤에도 [별도 심층 실험](../solutions/02_optimization/deep_review_02.md)을
진행했다. 18개 후보를 각각 독립 binary로 만들고 공식 1-round 1,000개,
20-round vector, 무작위 differential 100,000개를 다시 통과시킨 뒤 paired
측정을 수행했다. 전체 raw sample은
[`deep_results_02.txt`](../solutions/02_optimization/deep_results_02.txt)에 남겼다.

### 알고리즘 관점

두 라운드 합성 뒤 각 64비트 word는 서로 독립이지만, 각 word 내부에는
라운드마다 `RORX -> XOR -> BSWAP -> ADD`라는 직렬 경로가 남는다. modulo
덧셈의 carry 때문에 이 합성은 더 작은 rotate/XOR/add 형태로 닫히지 않는다.
word `i`의 한 라운드 변환을 `T_i`라 쓰면 정확한 합성은 다음과 같다.

```text
R^2(x)_i = T_(3-i)(T_i(x_i))
R^20     = (R^2)^10
```

이를 일반 함수의 거듭제곱처럼 exponentiation-by-squaring으로 줄이려면 합성
결과를 같은 작은 표현으로 보존해야 하지만, ADD의 carry 때문에 불가능했다.
일반 64비트 합성 함수를 table로 만들면 사실상 `2^64` mapping이 필요하다.

항상 byte-swapped 상태 `z=BSWAP64(x)`를 유지하는 표현도 시험했다. 이때
덧셈은 `z'=BSWAP64(BSWAP64(z)+A)`가 되어 두 번의 변환과 반대 방향 carry를
다시 처리해야 한다. rotation `43/7/29/14`도 byte 경계가 아니어서 byte table은
인접 byte의 비트와 carry 상태까지 가져야 했다. 결국 현재 instruction chain보다
짧아지지 않았다. 네 chain을 하나씩 직렬 계산한 대조군은 기준의 0.7305배
성능에 그쳐, 네 chain을 interleave해 instruction-level parallelism을 노출하는
현재 구성이 중요함을 확인했다.

### frontend, instruction/cache 관점

현재 BMI2 full-unroll helper는 1,267바이트다. 함수 진입에는 callee-saved
register push 네 개가 있지만 hot body에는 spill이
없고, 상수 8개와 상태 4개가 register에 남는다. 네 chain 각각의 핵심
dependency depth는 20라운드 x 약 4개 instruction, 즉 약 80단계다. 2.25GHz
VM에서 34--36ns는 약 77--81 cycle이므로 단순 latency 하한과 거의 같다.
남은 차이는 연산 수보다 instruction frontend, decoded-uop/code layout과 target
Intel의 latency 차이에 민감하다.

상수 pointer는 함수 진입 때 한 번만 읽혀 hot body 재접근이 없었다. literal
내장은 오히려 `movabs` encoding으로 symbol만 1,314바이트로 키웠다.
`target("bmi2")`는 runtime dispatch가 아니므로 이식할 때 CPUID 검사와 portable
fallback이 필요하다. 또한 caller와 callee의 target option이 다르면 GCC가
inline을 거부할 수 있으므로, 추가 flag가 없는 제출 경로는 BMI2 helper를
noinline/tail-call 형태로 유지했다. 제공 loop wrapper는 실제로 5바이트 tail
jump가 되어 19회 중복 loop 비용을 만들지 않는다.

### unroll5의 세션별 재측정

작은 715바이트 후보는 첫 run만 고르면 승자처럼 보이지만 이후 세 캠페인에서
모두 역전됐다.

| 세션 | flags | full 중앙값 | unroll5 중앙값 | paired 중앙값 | paired MAD |
|---|---|---:|---:|---:|---:|
| 전체 후보 1차 | `-O3` | 34.804 ns | 32.896 ns | 1.086728x | 0.040070x |
| 즉시 독립 재측정 | `-O3` | 53.939 ns | 55.559 ns | 0.971245x | 0.000755x |
| Intel tune 경로 확인 | `-O3 -mtune=alderlake` | 49.155 ns | 51.487 ns | 0.969304x | 0.115203x |
| host native | `-O3 -march=native` | 32.065 ns | 35.949 ns | 0.921385x | 0.058268x |

`-mtune=alderlake` 행은 AMD에서 compiler 경로만 확인한 것이며 Intel 성능
예측값이 아니다. 최종 Intel Core Ultra 7 255H/GCC 13.3.0의 서로 다른 두
세션에서 unroll5가 모두 1.02x 이상이고 MAD도 충분히 작을 때만 교체한다.
문제의 추가 flag 허용 문구와 `run_contest.sh` 수정 권한은 동일하지 않으므로
기본 `-O3`에서도 빌드되는 경로를 보존하고, 허용될 때 source에 특정 `arch=`를
박기보다 build command에서 `-march=native` 또는 `-mtune=native`를 비교한다.

### 심층 검증과 측정 기록

- AMD EPYC 7B12, GCC 12.2.0에서 logical CPU 2에 고정했다.
- 기본 build는 `-O3 -std=c11 -Wall -Wextra -Wpedantic -Werror -DNDEBUG`이고
  timer는 `CLOCK_MONOTONIC_RAW`다.
- 18개 구현 모두 공식 1-round 1,000개, 공식 20-round vector와 고정 seed
  differential 100,000개를 통과했다.
- 후보마다 독립 binary를 만들고 주소 modulo 4096, symbol/text 크기를
  `nm`과 `size`로 기록해 큰 함수끼리 code layout을 교란하지 않게 했다.
- invocation마다 300,000-call warm-up 뒤 sample당 2,000,000회, 총 15개
  sample을 쟀다. seeded random으로 기준/후보 순서를 뒤집고 인접
  `baseline_ns/candidate_ns`의 median과 MAD를 보고했다.

재현 명령:

```bash
python3 solutions/02_optimization/run_deep_review_02.py \
  --iterations 2000000 --warmup-iterations 300000 \
  --samples 15 --random-cases 100000 \
  --output /tmp/challenge02-deep.txt
```

## 결론

복원한 구조와 rotation은 모든 제공·random vector를 통과한다. 첫 최적화는
전체 byte reversal을 word reversal+`BSWAP64`로 축약한 것이고, 이번
최적화는 두 라운드 뒤 word 위치가 복원된다는 대수적 성질로 네 독립
chain을 만든 것이다. 10개 pair의 완전 전개와 BMI2 scalar가 이 host의
후보 선별에서 가장 빨랐고 제출 형태에서도 대체로 소폭 개선됐다. raw
sample과 불확실성을 함께 남겼으므로 target CPU에서 최종 선택을 그대로
재현할 수 있다.

## 참고 자료와 활용

- [ISO/IEC JTC1/SC22/WG14 N1570, C11 공개 위원회 초안](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) — `uint64_t`, unsigned modulo 연산과 유효 shift 범위를 유지하는 기준이다.
- [GCC, Byte-Swapping Builtins](https://gcc.gnu.org/onlinedocs/gcc/Byte-Swapping-Builtins.html) — 32-byte reverse를 네 `__builtin_bswap64`로 특수화한 근거다.
- [GCC, Common Function Attributes](https://gcc.gnu.org/onlinedocs/gcc/Common-Function-Attributes.html) — `aligned`, `noinline`, `noclone`, `always_inline`의 의미와 linker 정렬 한계를 확인했다.
- [GCC, x86 Function Attributes](https://gcc.gnu.org/onlinedocs/gcc/x86-Function-Attributes.html) — 기본 run script를 바꾸지 않고 helper에 BMI2 target을 국소 지정하는 방법이다.
- [Intel 64 and IA-32 Architectures Optimization Reference Manual](https://www.intel.com/content/www/us/en/developer/articles/technical/intel64-and-ia32-architectures-optimization.html)와 [Intel Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html) — scalar rotate/`RORX`와 AVX2 variable shift, shuffle, permute 후보의 instruction 특성을 비교했다.
- [Intel Core Ultra 7 255H 공식 사양](https://www.intel.com/content/www/us/en/products/sku/241751/intel-core-ultra-7-processor-255h-24m-cache-up-to-5-10-ghz/specifications.html) — 최종 CPU가 heterogeneous core와 AVX2를 가지므로 target에서 core affinity를 기록해야 한다는 근거다.
- [GCC 13.3 x86 Options](https://gcc.gnu.org/onlinedocs/gcc-13.3.0/gcc/x86-Options.html) — AMD VM의 `-march=native` 결과를 Intel target 결과로 간주하지 않고 별도 측정해야 하는 이유다.
- [Mytkowicz et al., *Producing Wrong Data Without Doing Anything Obviously Wrong!*](https://sape.inf.usi.ch/publications/asplos09.html) — code layout과 실행 순서만으로 benchmark 편향이 생길 수 있어 separate binary와 순서 교차를 사용했다.
- [Google Benchmark User Guide](https://github.com/google/benchmark/blob/main/docs/user_guide.md) — minimum warm-up, repetition, random interleaving, 통계와 JSON 보존의 기준이다.
- [NIST Measures of Scale](https://www.itl.nist.gov/div898/handbook/eda/section3/eda356.htm) — shared VM의 긴 tail에서 평균/표준편차뿐 아니라 median과 MAD를 보고하는 근거다.
- [Linux kernel CPUSETS documentation](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v1/cpusets.html) — CPU affinity를 metadata와 함께 기록하는 시스템 근거다.
