# 3. 네트워크보안 - TLS 1.2 AES-GCM record 위조

## 문제

`tls_live.pcap`에는 TLS 1.2 기반 통신이 들어 있고, 서버에서 지사로 전달되는 application data 4개가 포함되어 있다. 문제 본문이 3번째 record의 원래 평문을 급여 `0100` 설정 메시지로 직접 제공하며, 목표는 이를 `0500`으로 바꾼 뒤에도 유효한 TLS application data로 인식되는 record 전체를 만드는 것이다. 즉 원래 평문은 pcap을 복호화해 얻은 값이 아니라 문제에서 주어진 known plaintext다.

평문 형식:

```text
action=<cmd>&uid=<4-digit>&amt=<4-digit>&month=<6-digit>
```

제출물은 Ethernet/IP/TCP header를 제외한 TLS record hex 문자열과 분석·구현 보고서다. 최종 record는 다음 77바이트다.

```text
17030300489c269a9f29810ab0a99141d1d84c3df6bfdcdb7dec7cf30462db203fbc36a29772edbf159643b468f1f1e520e7341daee867a49665542cd9f01f5a9c906b73ba3e13bbfea0e98a18
```

## 배경지식

### TLS 1.2 AES-GCM record와 nonce

ServerHello가 선택한 cipher suite는 `0xc02f`, 즉 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`다. TLS 1.2 GCM record의 wire format은 다음과 같다.

```text
TLS header: type || version || length
fragment: explicit_nonce || ciphertext || tag
```

전체 GCM nonce는 해당 TLS write state의 4바이트 fixed salt와 record에 실리는 8바이트 explicit nonce를 연결한 96비트 값이다.

```text
nonce = write_salt[4] || nonce_explicit[8]
```

같은 연결·방향·cipher epoch에서는 key와 fixed salt가 같으므로 explicit nonce가 같으면 전체 nonce도 같다. GCM AEAD에는 CBC 방식의 TLS padding이나 별도 HMAC이 없고 16바이트 GCM tag가 암호문과 AAD를 함께 인증한다.

AAD는 정확히 13바이트다.

```text
AAD = seq_num[8] || type[1] || version[2] || plaintext_length[2]
```

여기서 `plaintext_length`는 AEAD가 암호화한 TLSCompressed fragment의 길이다. record header의 `length`는 explicit nonce·ciphertext·tag를 합한 wire fragment 길이므로 두 값을 구분해야 한다.

### GCM nonce reuse의 위험

AES-GCM은 같은 key에서 nonce를 절대 재사용하면 안 된다. nonce가 재사용되면 다음 두 가지가 동시에 발생한다.

1. CTR keystream이 재사용되어 known plaintext가 있으면 ciphertext를 원하는 평문으로 바꿀 수 있다.
2. 같은 `E_K(J0)`가 tag에 사용되므로, 여러 record의 tag 차분에서 GHASH key `H`에 대한 방정식을 세울 수 있다.

GCM tag는 다음 형태다.

```text
H   = AES_K(0^128)
S   = AES_K(J0)
tag = S xor GHASH_H(AAD, C)
```

같은 nonce record는 `J0`가 같아 `S` 역시 같다. 두 tag를 XOR하면 `S`가 사라진다.

```text
tag1 xor tag2 = GHASH_H(AAD1, C1) xor GHASH_H(AAD2, C2)
```

이 식은 `H`에 대한 GF(2^128) 다항식이 되므로 session key를 알지 못해도 `H`와 `S`를 복원해 새 tag를 만들 수 있다.

## 풀이

### 1. pcap에서 TLS application record 추출

pcap global header의 link type은 `DLT_IPV4(228)`다. 서버 방향 `10.0.0.1:443 -> 10.0.0.2:54321`의 TCP segment를 sequence number 순으로 정렬하고 overlap을 제거해 byte stream을 재조립했다. 각 TLS record는 5바이트 header의 length를 기준으로 분리했고, ServerHello에서 TLS 1.2와 cipher suite `0xc02f`를 확인했다.

서버가 ChangeCipherSpec를 전송하면 새 write state의 TLS sequence number가 0으로 초기화된다. 그 뒤의 encrypted Finished record가 `seq=0`을 사용하므로 이후 application data 4개의 sequence number는 `1,2,3,4`다. 분리 결과는 다음과 같다.

| application record | TLS seq | explicit nonce | ciphertext | wire fragment |
|---:|---:|---|---:|---:|
| 1 | 1 | `9c269a9f29810ab0` | 34 bytes | 58 bytes (`0x003a`) |
| 2 | 2 | `9c269a9f29810ab0` | 50 bytes | 74 bytes (`0x004a`) |
| 3, 위조 대상 | 3 | `9c269a9f29810ab0` | 48 bytes | 72 bytes (`0x0048`) |
| 4 | 4 | `9c269a9f29810ab1` | 40 bytes | 64 bytes (`0x0040`) |

처음 세 record는 같은 연결·방향·cipher epoch에서 explicit nonce를 재사용했다. 따라서 4바이트 fixed salt까지 포함한 전체 96비트 nonce와 CTR keystream, `S=E_K(J0)`가 모두 같다. 4번 record의 explicit nonce가 `...ab1`로 변하는 것도 parser가 record 경계를 올바르게 찾았는지 확인하는 대조군이 된다.

### 2. 정확한 AAD와 GHASH key 복원

위조 대상은 application record 3번이므로 TLS sequence number는 3, type은 `0x17`, version은 `0x0303`, 평문 길이는 48바이트 `0x0030`이다. 따라서 AAD는 다음 13바이트다.

```text
0000000000000003 || 17 || 0303 || 0030
= 00000000000000031703030030
```

record header의 `0048`은 `8-byte nonce + 48-byte ciphertext + 16-byte tag = 72` 인 wire fragment 길이고, AAD의 `0030`은 암호화 전 평문 길이다. 이 두 길이를 혼동하면 위조 tag가 일치하지 않는다.

GHASH는 다음 체에서 계산한다.

```text
GF(2^128) = GF(2)[x] / (x^128 + x^7 + x^2 + x + 1)
```

AAD 13바이트는 GHASH 내부에서 3개 zero byte로 블록 정렬되고, ciphertext도 16바이트 배수로 내부 정렬된다. 마지막에 `len(AAD)*8 || len(C)*8`의 128비트 length block이 붙는다. 이 zero padding은 GHASH 인코딩의 일부일 뿐 wire에 전송되는 TLS padding이 아니다. 목표 ciphertext는 정확히 48바이트이므로 ciphertext 뒤의 zero padding은 없다.

GHASH block을 `X_1,...,X_m`으로 두면 다음 recurrence가 `H`에 대한 다항식 `P(H)`를 만든다.

```text
Y_0 = 0
Y_i = (Y_(i-1) xor X_i) * H
GHASH_H(AAD, C) = Y_m = P(H)
```

1번과 2번 record에서 `S`를 제거하면 다음 6차 방정식을 얻는다. 2번 ciphertext가 50바이트이므로 AAD block 1개, ciphertext block 4개, length block 1개가 되어 최고차항이 6차다.

```text
F_12(H) = P_1(H) xor P_2(H) xor T_1 xor T_2 = 0
```

구현은 다음 GCD로 GF(2^128) 안의 선형 인수들만 분리한 뒤 각 근을 분할했다.

```text
gcd(F_12(X), X^(2^128) - X)
```

NIST GCM은 128비트 문자열의 왼쪽 bit부터 `x^0,x^1,...`의 계수로
대응시키지만, solver의 일반 다항식 연산은 정수 bit 0을 상수항 계수로
본다. 따라서 표현 경계에서 128비트 bit reverse를 적용한다. 가장 단순한
경계 예시는 다음과 같다.

```text
NIST block 0x80000000000000000000000000000000  <->  polynomial integer 1
NIST block 0x40000000000000000000000000000000  <->  polynomial integer 2 (= x)
```

solver는 실행할 때 첫 번째 값을 GCM 표현의 곱셈 항등원으로 사용해 임의
probe와 곱한 값이 probe 그대로인지 self-test한다.

1·2번 record로 만든 6차식에서 실제로 얻은 체 내부 root는 1개였고,
3번 record까지 포함해 `T_i xor P_i(H)`가 모두 같은지 검사한 뒤에도
1개가 남았다.

| 단계 | 후보 수 |
|---|---:|
| `F_12`의 `GF(2^128)` root | 1 |
| 3번 record의 동일 `S` 조건 통과 | 1 |

```text
H         = 112332a84132bc0c5c23a61037723683
S=E_K(J0) = 1e023d8461003896981f1441c5feab90
```

`H`는 GCM authentication subkey이지 AES session key 자체가 아니다. 그러나 재사용된 nonce에 대한 `S`와 `H`를 모두 알면 그 nonce로 임의의 ciphertext와 AAD를 인증할 수 있다.

### 3. 평문 변경

목표 record는 3번째 application data다. 아래 원문은 문제 본문에서
직접 제공한 known plaintext이며 pcap에서 별도로 복호화한 결과가 아니다.
원문과 목표문은 모두 48바이트이고 오직 한 바이트만 다르다.

원문:

```text
action=set_salary&uid=0007&amt=0100&month=202603
```

목표:

```text
action=set_salary&uid=0007&amt=0500&month=202603
```

변경 위치는 0부터 세었을 때 offset 32이다. ASCII `'1'=0x31`을 `'5'=0x35`로 바꾸므로 delta는 `0x04`이고, 기존 ciphertext의 해당 byte `0xf5`는 `0xf1`이 된다.

```text
0x31 xor 0x35 = 0x04
0xf5 xor 0x04 = 0xf1
```

CTR 모드의 `C=P xor KS`에서 같은 keystream `KS`를 재사용하므로 암호화 key를 모르더라도 다음처럼 ciphertext를 변경할 수 있다.

```text
C' = C xor P xor P'
```

```text
old C = a99141d1d84c3df6bfdcdb7dec7cf30462db203fbc36a29772edbf159643b468f5f1e520e7341daee867a49665542cd9
new C = a99141d1d84c3df6bfdcdb7dec7cf30462db203fbc36a29772edbf159643b468f1f1e520e7341daee867a49665542cd9
```

길이가 바뀌지 않았으므로 TLS header와 AAD는 그대로다.

### 4. tag 재계산

`H`를 알기 때문에 새 ciphertext에 대한 GHASH를 계산할 수 있다. nonce와 AAD가 그대로이므로 `S=E_K(J0)`도 기존과 같다.

```text
S    = old_tag xor GHASH_H(AAD, old_C)
tag' = S xor GHASH_H(AAD, new_C)
     = old_tag xor GHASH_H(old) xor GHASH_H(new)
```

중간값을 대입하면 다음과 같다.

```text
old tag   = b0d6e0ac2be205621f7ea4a034519f95
GHASH old = aed4dd284ae23df48761b0e1f1af3405
S         = 1e023d8461003896981f1441c5feab90
GHASH new = ee1d6718f16b4b2ca60cafbf65172188
new tag   = f01f5a9c906b73ba3e13bbfea0e98a18
```

### 5. 최종 record 바이트 레이아웃

최종 record를 wire offset별로 분해하면 다음과 같다.

| byte offset | 크기 | 의미 | 값 |
|---:|---:|---|---|
| `0` | 1 | ContentType: application data | `17` |
| `1..2` | 2 | TLS version 1.2 | `0303` |
| `3..4` | 2 | 암호화 fragment 길이 | `0048` = 72 |
| `5..12` | 8 | explicit nonce | `9c269a9f29810ab0` |
| `13..60` | 48 | forged ciphertext | `a991...42cd9` |
| `61..76` | 16 | forged GCM tag | `f01f5a9c906b73ba3e13bbfea0e98a18` |

fragment는 `8+48+16=72` 바이트, TLS header까지 포함한 record는 `5+72=77` 바이트이다. 따라서 제출 hex는 개행을 제외하면 154문자여야 한다.

최종 위조 TLS record:

```text
17030300489c269a9f29810ab0a99141d1d84c3df6bfdcdb7dec7cf30462db203fbc36a29772edbf159643b468f1f1e520e7341daee867a49665542cd9f01f5a9c906b73ba3e13bbfea0e98a18
```

## 구현

[`solve_03_tls_gcm_nonce_reuse.py`](../solutions/solve_03_tls_gcm_nonce_reuse.py)는 외부 패키지 없이 Python 표준 라이브러리로 다음 과정을 모두 수행한다.

1. ZIP에서 pcap을 읽고 magic, endian, link type, packet 길이를 검사한다.
2. 서버 TCP segment를 sequence number로 재조립하고 TLS record 길이를 엄격히 검사한다.
3. ChangeCipherSpec 이후의 TLS sequence number와 application record의 nonce 패턴을 복원한다.
4. GCM 표현의 `0x8000...00` 항등원 test를 거친 뒤 GF(2^128) 곱셈·역원·다항식 GCD·유한체 인수분해를 구현해 `H`를 찾고 단계별 후보 수를 출력한다.
5. 평문 delta로 ciphertext를 변경하고 `S` 및 새 GHASH로 tag를 만든다.
6. record 길이와 제출 파일까지 동기화됐는지 검증한다.

다항식 분할에서 쓰는 난수는 `random.seed(3)`으로 고정해 실행을 재현 가능하게 했다. 난수는 알고리즘의 인수 분할을 위해서만 사용하며, 결과 후보는 세 record의 tag 방정식으로 결정론적으로 검증한다.

## 재현 및 검증

저장소 루트에서 다음 명령을 실행한다.

```bash
python3 solutions/solve_03_tls_gcm_nonce_reuse.py
```

스크립트는 아래 조건을 assertion으로 검증한 후에만 최종 record를 출력한다.

- ServerHello cipher suite가 `0xc02f`이고 application sequence number가 `1..4`인지 검사한다.
- application data 1∼3번의 explicit nonce는 같고 4번은 다른지 검사한다.
- NIST MSB-first 표현의 `0x8000...00`이 곱셈 항등원으로 동작하는지 검사한다.
- 복원된 `H` 후보가 하나이고 세 record의 `T xor GHASH`가 같은 `S`를 만드는지 검사한다.
- 기존 ciphertext에서 유도한 keystream으로 새 ciphertext를 확인하면 정확히 `amt=0500`인지 검사한다.
- `new_tag xor GHASH(new) == S`를 다시 계산해 인증 식을 만족하는지 검사한다.
- TLS header의 `length=72`, 전체 길이 77바이트, 예상 hex, [`forged_record.txt`](../submissions/03/forged_record.txt)의 값이 모두 일치하는지 검사한다.

실제 검증 마지막 출력은 다음과 같다.

```text
forged tag = f01f5a9c906b73ba3e13bbfea0e98a18
forged TLS record = 17030300489c269a9f...13bbfea0e98a18
verification = pcap, nonce reuse, H, E_K(J0), plaintext delta, tag, length, and submission checks passed
```

제출 패키지에는 record hex와 이 분석을 PDF로 만든 [`report.pdf`](../submissions/03/report.pdf)를 함께 넣었다.

## 참고 자료와 활용

- [IETF RFC 5246, *The Transport Layer Security (TLS) Protocol Version 1.2*](https://www.rfc-editor.org/rfc/rfc5246.html#section-6.2.3.3) — AEAD additional data의 `seq_num || type || version || length`, TLS record 구조, cipher state별 sequence number를 적용했다.
- [IETF RFC 5288, *AES Galois Counter Mode (GCM) Cipher Suites for TLS*](https://www.rfc-editor.org/rfc/rfc5288.html#section-3) — TLS 1.2 AES-GCM의 4-byte salt와 8-byte explicit nonce, 128-bit tag, nonce 고유성 조건을 record 해석에 활용했다.
- [NIST SP 800-38D, *Galois/Counter Mode (GCM) and GMAC*](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-38d.pdf) — `GHASH_H(AAD,C)`, counter-mode 암복호, tag 계산식과 key/IV 고유성 요구사항을 2~4절의 기준으로 활용했다.
- [David A. McGrew and John Viega, “The Security and Performance of the Galois/Counter Mode (GCM) of Operation”](https://eprint.iacr.org/2004/193.pdf) — GF(2^128) universal hash를 다항식으로 표현하고 복원한 `H` 후보를 검증하는 solver 설계에 활용했다.
- [Antoine Joux, “Authentication Failures in NIST version of GCM”](https://csrc.nist.gov/CSRC/media/Projects/Block-Cipher-Techniques/documents/BCM/Comments/800-38-series-drafts/GCM/Joux_comments.pdf) — 동일 IV의 tag 차분에서 authentication subkey를 복원하고 새 ciphertext/tag를 위조하는 공격 절차의 직접 근거로 활용했다.
