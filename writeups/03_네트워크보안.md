# 3. 네트워크보안 - TLS 1.2 AES-GCM record 위조

## 문제

`tls_live.pcap`에는 TLS 1.2 기반 통신이 들어 있고, 서버에서 지사로 전달되는 application data 4개가 포함되어 있다. 3번째 record의 평문은 급여를 `0100`으로 설정하는 메시지이며, 목표는 이를 `0500`으로 바꾼 뒤에도 유효한 TLS application data로 인식되는 record 전체를 만드는 것이다.

평문 형식:

```text
action=<cmd>&uid=<4-digit>&amt=<4-digit>&month=<6-digit>
```

제출물은 Ethernet/IP/TCP header를 제외한 TLS record hex 문자열이다.

## 배경지식

### TLS 1.2 AES-GCM record 구조

TLS 1.2의 AES-GCM record는 대략 다음 구조다.

```text
TLS header: type || version || length
fragment: explicit_nonce || ciphertext || tag
```

인증에 들어가는 AAD는 TLS sequence number, record type, version, plaintext length를 포함한다.

### GCM nonce reuse의 위험

AES-GCM은 같은 key에서 nonce를 절대 재사용하면 안 된다. nonce가 재사용되면 다음 두 가지가 동시에 발생한다.

1. CTR keystream이 재사용되어 known plaintext가 있으면 ciphertext를 원하는 평문으로 바꿀 수 있다.
2. 같은 `E_K(J0)`가 tag에 사용되므로, 여러 record의 tag 차분에서 GHASH key `H`에 대한 방정식을 세울 수 있다.

GCM tag는 다음 형태다.

```text
tag = E_K(J0) xor GHASH_H(AAD, C)
```

같은 nonce record 두 개를 빼면 `E_K(J0)`가 사라진다.

```text
tag1 xor tag2 = GHASH_H(AAD1, C1) xor GHASH_H(AAD2, C2)
```

이 식은 `H`에 대한 GF(2^128) 다항식이 된다.

## 풀이

### 1. pcap에서 TLS application record 추출

Raw IPv4 pcap을 직접 파싱해 서버 `10.0.0.1:443`에서 클라이언트로 가는 TCP payload를 이어 붙였다. TLS handshake 이후 application data record만 골라내면 다음과 같다.

```text
seq=1 nonce_explicit=9c269a9f29810ab0 ciphertext_len=34
seq=2 nonce_explicit=9c269a9f29810ab0 ciphertext_len=50
seq=3 nonce_explicit=9c269a9f29810ab0 ciphertext_len=48
seq=4 nonce_explicit=9c269a9f29810ab1 ciphertext_len=40
```

처음 3개 record가 같은 explicit nonce를 사용한다. 이것이 취약점이다.

### 2. GHASH key 복원

처음 3개 record의 AAD, ciphertext, tag를 사용해 `H` 후보를 구했다. 구현에서는 GCM의 bit ordering을 다항식 표현과 맞추기 위해 128비트 bit reverse를 사용했다.

복원 결과:

```text
H = 112332a84132bc0c5c23a61037723683
```

3개 record 모두에 대해 같은 `E_K(J0)` 값을 만들기 때문에 후보는 하나로 결정된다.

### 3. 평문 변경

목표 record는 3번째 application data다. 문제 예시의 평문 길이와 ciphertext 길이가 모두 48바이트로 일치한다.

원문:

```text
action=set_salary&uid=0007&amt=0100&month=202603
```

목표:

```text
action=set_salary&uid=0007&amt=0500&month=202603
```

CTR 모드에서는 같은 위치의 plaintext delta를 ciphertext에 XOR하면 된다.

```text
C' = C xor P xor P'
```

### 4. tag 재계산

`H`를 알기 때문에 새 ciphertext에 대한 GHASH를 계산할 수 있다. 같은 nonce를 유지하므로 `E_K(J0)`는 기존 tag에서 제거해 재사용한다.

```text
tag' = tag xor GHASH_H(old) xor GHASH_H(new)
```

최종 위조 TLS record:

```text
17030300489c269a9f29810ab0a99141d1d84c3df6bfdcdb7dec7cf30462db203fbc36a29772edbf159643b468f1f1e520e7341daee867a49665542cd9f01f5a9c906b73ba3e13bbfea0e98a18
```

## 검증

재현 명령:

```bash
python3 solutions/solve_03_tls_gcm_nonce_reuse.py
```

추가 assertion으로 확인한 내용:

- application data 1, 2, 3번의 explicit nonce가 동일하다.
- 4번 record는 nonce가 다르다.
- 복원된 `H`는 `112332a84132bc0c5c23a61037723683`이다.
- `0100 -> 0500`에 해당하는 plaintext delta가 ciphertext delta와 일치한다.
- 새 tag를 GHASH로 재계산한 forged record가 위 hex와 일치한다.

## 참고 자료와 활용

- [IETF RFC 5246, *The Transport Layer Security (TLS) Protocol Version 1.2*](https://www.rfc-editor.org/rfc/rfc5246.html) — pcap에서 `type || version || length` record를 파싱하고 TLS sequence number를 AAD에 넣는 1절 구현에 활용했다.
- [IETF RFC 5288, *AES Galois Counter Mode (GCM) Cipher Suites for TLS*](https://www.rfc-editor.org/rfc/rfc5288.html) — TLS 1.2 AES-GCM의 4-byte salt와 8-byte explicit nonce, 128-bit tag, nonce 고유성 조건을 record 해석에 활용했다.
- [NIST SP 800-38D, *Galois/Counter Mode (GCM) and GMAC*](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-38d.pdf) — `GHASH_H(AAD,C)`, counter-mode 암복호, tag 계산식과 key/IV 고유성 요구사항을 2~4절의 기준으로 활용했다.
- [David A. McGrew and John Viega, “The Security and Performance of the Galois/Counter Mode (GCM) of Operation”](https://eprint.iacr.org/2004/193.pdf) — GF(2^128) universal hash를 다항식으로 표현하고 복원한 `H` 후보를 검증하는 solver 설계에 활용했다.
- [Antoine Joux, “Authentication Failures in NIST version of GCM”](https://csrc.nist.gov/CSRC/media/Projects/Block-Cipher-Techniques/documents/BCM/Comments/800-38-series-drafts/GCM/Joux_comments.pdf) — 동일 IV의 tag 차분에서 authentication subkey를 복원하고 새 ciphertext/tag를 위조하는 공격 절차의 직접 근거로 활용했다.
